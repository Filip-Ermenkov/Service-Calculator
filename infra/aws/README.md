# Staging deploy role (GitHub Actions OIDC)

One-time AWS bootstrap so `.github/workflows/ci.yml`'s `deploy-staging` job can run `sst deploy --stage staging` without stored AWS keys. It has to exist *before* SST/CI can run, so it's **applied once by hand via the AWS CLI** (see the root README's Deploying section for the full command sequence).

> **Update (2026-07-31): this role + inline policy are now MANAGED by the foundational Terraform stack** (`infra/terraform/iam.tf`) — imported 2026-07-31. The `github-actions-deploy-policy.json` in this folder is therefore the **single source of truth**: change it and run `terraform apply` (**not** `aws iam put-role-policy`), and `terraform plan` continuously drift-checks file vs live. The import confirmed **file = live** — no permission/trust diff, only the three management tags were added. Note the inline policy's real AWS name is **`bulbau-staging-deploy`** (distinct from this JSON's filename). The hand-push CLI commands below are retained only for the original bootstrap / disaster-recovery context.

> **Account note (2026-07-27):** the committed JSON files now carry the **new dedicated account ID `847321857537`** (`service-calculator-production`); the app was migrated there from the shared `acc-test` account (`176971015975`). See `docs/PROGRESS.md` → "AWS account migration".
>
> **Fresh-account lesson worth knowing:** the *old* account's stack was first bootstrapped **by an admin**, so the restricted CI role rarely had to *create* resources. In the new account the CI role creates **everything** from scratch, which exposed real policy gaps below (each a global service the region-scoped statement never covered): `iam:CreateRole` on OpenNext's stage-truncated role names, and `cloudfront-keyvaluestore:*`. A cleaner path for any future fresh-account bootstrap is to run the **very first `sst deploy` with admin credentials** (so all `Create*` happen once under admin), after which the restricted CI role only ever *updates*.

## Files

- `github-actions-trust-policy.json` — trust policy for the IAM role. Scoped with `token.actions.githubusercontent.com:sub` to an **array** of `repo:Filip-Ermenkov/Service-Calculator:environment:staging` **and** `…:environment:production` (widened 2026-07-31 when the production stage stood up — the same role serves both stages; a `production`-Environment job's `sub` claim wouldn't match a staging-only value, so `AssumeRoleWithWebIdentity` would be denied). Environment-scoped rather than branch-scoped because the deploy jobs set `environment:`, which changes the shape of GitHub's OIDC `sub` claim (see [GitHub's OIDC-in-AWS docs](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)). Replace `ACCOUNT_ID` with the real 12-digit AWS account ID before use.
- `github-actions-deploy-policy.json` — permission policy attached to that role. The bootstrap (`ManageBootstrap*`) and `ManageSecrets` statements are copied from [SST's own documented IAM policy](https://sst.dev/docs/iam-credentials) — those are genuinely scoped to `sst-*`-prefixed resources. The `DeploymentsScopedToRegion` statement is deliberately broad (SST's own docs say hand-enumerating every action their components might need is tedious and error-prone) but constrained to `eu-central-1` via `aws:RequestedRegion`, and backstopped by an explicit `Deny` on the highest-risk IAM/org/billing actions — a region condition alone doesn't meaningfully limit IAM, CloudFront, or Route 53, since those are global services. Replace `ACCOUNT_ID` here too.
- `ManageCloudFront` exists as its own unconditioned statement because of that same global-service gap: CloudFront's control-plane calls don't satisfy `aws:RequestedRegion: eu-central-1`, so `DeploymentsScopedToRegion` silently doesn't cover them — first hit as a `cloudfront:CreateInvalidation` AccessDenied on the first real `deploy-staging` CI run. **It now also grants `cloudfront-keyvaluestore:*`** (added 2026-07-27): SST's `Nextjs` component uses a CloudFront **KeyValueStore** (`WebKvKeys`) for routing, which is a *separate IAM service prefix* from `cloudfront:*` and also global — it first denied on the fresh-account deploy. **This prediction came true (2026-07-31):** standing up the `production` custom domain (`bulbau.lu`) hit exactly this gap. The CloudFront cert must be ACM in **us-east-1** and Route 53 is a **global** service, so both were denied by the `eu-central-1`-scoped Allow. Fixed by adding two statements: **`ManageAcmCertsUsEast1`** (ACM request/describe/tag/delete, conditioned on `aws:RequestedRegion us-east-1`) and **`ManageRoute53RecordsInAppZone`** + **`Route53ReadChangesAndListZones`** (zone-scoped record writes + `route53:ListTagsForResource` — which SST's `getZone` lookup calls and which was the first-attempt `AccessDenied` — plus global `GetChange`/`ListHostedZones*`). Same lesson: unconditioned/region-correct statements for global or cross-region services, never a stretched `eu-central-1` condition.
- `ManageAppIamRoles` is the IAM instance of that exact same global-service gap. IAM calls carry no region, so `DeploymentsScopedToRegion` never covers `iam:CreateRole` and friends. **Scope broadened to `role/*` (2026-07-27), backstopped by a new `ProtectCriticalRoles` Deny.** Originally scoped to the app-stage prefix `role/bulbau-lu-staging-*`, but that proved unworkable in the fresh account: SST's `Nextjs` component names some internal execution roles with a **stage-truncated** prefix (`stagi-WebRevalidation…`, truncated to fit IAM's 64-char limit), not `bulbau-lu-staging-*`, so `iam:CreateRole` was denied. Prefix-matching is unpredictable (truncation varies with the logical name), so the resource was widened to `arn:aws:iam::847321857537:role/*` — acceptable because **this account is single-app** (all roles in it are this app's) — and a new **`ProtectCriticalRoles` Deny** guards the roles that matter (`OrganizationAccountAccessRole`, the SSO `aws-reserved/sso.amazonaws.com/*` roles, and the deploy role itself) from being modified/deleted/passed, so the broad Allow can't be abused. The high-risk IAM verbs (`iam:CreateUser`, `iam:UpdateAssumeRolePolicy`, `iam:AttachUserPolicy`, …) remain blocked by `ExplicitDenyHighRiskActions`. **Since 2026-07-31 this policy + the role are managed by Terraform** (`infra/terraform/iam.tf`, which sources these JSON files via `file()`), so the way to push an edit live is **`terraform apply`** — editing this file alone still does not change AWS, but `terraform plan` now continuously drift-detects file-vs-live. (Historically it was hand-pushed with `aws iam put-role-policy`, and the "file ≠ live" gap bit twice during the migration — Terraform closes that.)

## Before this is "done"

Per SST's own "Minimize permissions" guidance: run IAM Access Analyzer against the deploy role's CloudTrail activity and replace `DeploymentsScopedToRegion` with the generated least-privilege policy. **Note (2026-07-31): production reuses this same role** (no separate production role — the `role/*` scope + both-environment trust cover it), so the CloudTrail history now spans both stages incl. the ACM/Route 53 custom-domain calls; the Analyzer pass will capture those too. Tracked as a Phase 7 follow-up in `docs/PROGRESS.md` → "Immediate next steps". **Status (2026-07-21): staging is live and has run real migrated deploys plus the Phase 2 public-site deploy and the Phase 3/Phase 4 deploys — including the `Pdf` function's own execution role (the first role CI's restricted deploy role provisioned itself, exercising the new `ManageAppIamRoles` statement).** So there's now a good, representative stretch of CloudTrail history — the generated least-privilege policy will now also capture the IAM role-lifecycle actions, not just the region-scoped app actions. This is an active follow-up tracked in `docs/PROGRESS.md` → "Immediate next steps" — not a blocker for current work. Two things that add **nothing** to this policy's surface: the CI database-migration step (it connects to Neon directly, no AWS role), and Phase 2's two new SST secrets (`SiteUrl`/`AllowIndexing`) — SST secrets live in SSM Parameter Store under the `sst-*` prefix already covered by the `ManageSecrets` statement.
