> **★ NEWEST (2026-08-04) — On-demand CloudFront invalidation is BUILT and verified live on staging, and it exposed + fixed a latent revalidation bug in the auto-translation hook.** This is the HIGH-priority "proper fix" that "Immediate next steps" item 3b tracked; the interim `revalidate=10s` workaround is now unwound (content pages are back to `revalidate=300`). A fresh session MUST know: **(a) How it works.** OpenNext's automatic CDN invalidation is a dummy no-op by default (verified; OpenNext 3.4+ ships a built-in `cloudfront` override, but it needs `CLOUDFRONT_DISTRIBUTION_ID` as a literal env var — impossible in one pass, because the server function would depend on the distribution while the distribution depends on the function URL = the **SST #5990 cycle**). So the id is written to an **SSM parameter** `/bulbau-lu/<stage>/web-cdn-distribution-id` created **after** the `Web` Nextjs component in `sst.config.ts` (parameter→distribution, never the reverse ⇒ no cycle); the server function receives only the parameter **NAME** as a static env `CDN_DISTRIBUTION_ID_PARAM`; and `src/lib/cdn/invalidate.ts` reads the id at runtime (cached per warm instance) and calls `CreateInvalidation('/*')` from the revalidate path. New deps: `@aws-sdk/client-cloudfront` + `@aws-sdk/client-ssm`. Runtime IAM (on the Web function via SST `permissions`): `ssm:GetParameter` scoped to the exact param ARN + `cloudfront:CreateInvalidation` on `arn:aws:cloudfront::*:distribution/*`. **The deploy role needed NO change** (SSM create is covered by the region-blanket allow; `cloudfront:*` + `iam:PutRolePolicy role/*` were already present) — the first slice this year with no IAM gap. The module never throws and is a **silent no-op when `CDN_DISTRIBUTION_ID_PARAM` is unset** (local/CI/tests need no AWS access). **(b) The latent bug it exposed (critical for a fresh session).** On-demand revalidation had been **silently broken for translated content since Phase 5**, masked by the old 10s ISR window. The auto-translation `afterChange` hook sets `req.context.disableRevalidate=true` before its nested FR/DE writes and relied on **restoring** it so the top-level save's revalidate hook would still fire — but that restore does NOT reach the outer save on OpenNext/Payload (**proven from CloudWatch: every revalidate fire logged `disableRevalidate=true`, never `false`**), so the main save's `revalidatePath` AND the CDN purge were both skipped. Fix: the translation hook now **leaves the flag set** (deliberately suppressing the standalone revalidate hook for nested AND top-level writes) and calls **`revalidatePublicSiteNow()` itself, exactly once**, at the end — `src/lib/revalidate.ts` exports it, `src/lib/translation/hook.ts` calls it. Non-translated saves/deletes still use the standalone hook. This relies only on the flag *propagating* (which works), not being *restored* (which didn't). **(c) Deploy/debug gotchas.** (i) The staging Web function is `…-WebServerEucentral1Function-useatxhz` but it **logs to a differently-suffixed group** `/aws/lambda/…-WebServerEucentral1Function-ewutanmb` (Lambda custom log-group) — tail the `ewutanmb` group, not the one matching the function name. > **(2026-08-02) — Phase 5 part 1 (CMS auto-translation) is BUILT, tested, and confirmed working on staging.** CMS content now auto-translates **EN → FR/DE on save**, so FR/DE pages show real translated content instead of the EN fallback. A fresh session MUST know: **(a) Engine is AWS Translate, NOT DeepL.** DeepL retired its recurring free API tier (new accounts get a one-time 1M-char allowance, then paid) — verified against DeepL's 2026 pricing. AWS Translate is $15/M chars + **2M chars/mo free for 12 months**, needs **no new secret and no new sub-processor** (it authenticates via the Lambda execution role; the deploy policy gained `translate:TranslateText`, `resources:['*']`), and supports a FORMAL register for fr+de. This site's entire content is <100K chars so cost is cents/month (free the first year). The engine is isolated behind `src/lib/translation/provider.ts` — swapping it touches only that file. **(b) Architecture is a SYNCHRONOUS `afterChange` hook** (a deliberate, researched deviation from TECHSPEC §6.7's Jobs-Queue proposal): Payload's `autoRun` isn't for serverless, Next's `after()` is **unsupported on OpenNext AWS** (verified), and a real async worker would need Payload bundled into a second Lambda — disproportionate for a single-admin CMS. The sync hook is made safe+fast by: **pacing** AWS calls under the 20 req/s quota (no throttle → no SDK backoff — the un-paced burst was a "30s+ save" cause), a hard **12s in-save deadline** that can't throw, an explicit **30s Lambda `server.timeout`** (afterChange runs INSIDE the save transaction, so a timeout there would ROLL THE PUBLISH BACK — this was the "hard refresh shows old data" bug), **sequential** locales (they share one Postgres transaction), and a **bulletproof recursion guard that MUTATES `req.context.skipAutoTranslate`** rather than passing the ambiguous per-call `context` arg (a guard that didn't reach the nested write made our FR/DE writes re-translate endlessly → the "3-minute create"). Field selection is **self-healing + override-safe**: a field is (re)translated iff its EN source changed OR the target is still the untranslated EN fallback (`base` deep-equals `source`), so pre-existing/untouched/failed fields fill on the next save while real translations and manual per-locale overrides are preserved. **(c) Migration-free, no schema change** (localization was enabled in Phase 1); new dep `@aws-sdk/client-translate`; gated by `TRANSLATE_ENABLED='true'` (SST sets it on deployed stages; unset locally/CI ⇒ no-op, FR/DE fall back to EN). **(d) A CloudFront cache gotcha was found + worked around:** OpenNext's automatic CDN invalidation is a **dummy no-op by default** (verified in OpenNext docs), so `revalidatePath` refreshes the S3 origin but **CloudFront keeps serving the stale page until `s-maxage`** (was `revalidate=300` → up to 5 min = the ">1 min stale" bug). Worked around by lowering every content page to `revalidate=10`, `next.config` `experimental.staleTimes {dynamic:0, static:30}` (client Router-Cache floor is 30s — `0` is rejected), and `prefetch={false}` on the language switcher. The PROPER fix — **on-demand CloudFront invalidation** — is a HIGH-priority next step (blocked only by SST not cleanly exposing the distribution ID: circular-dep, SST issue #5990). **(e) NOT done: Phase 5 part 2** — the dedicated Translation Management admin screen (§5.7). Overrides already work today by switching the admin locale and editing FR/DE directly; the screen is a convenience surface over that. ## Phase 6 — Contact form + spam protection (built + verified on staging + deployed to production 2026-08-06)

### The homework (current best practice, verified at implementation time — not from memory)
- **Cloudflare Turnstile server-side verification** (verified against Cloudflare's official "Validate the token" + "Testing" docs, last updated 2026-05): Siteverify is `POST https://challenges.cloudflare.com/turnstile/v0/siteverify` with `secret`/`response`/(optional)`remoteip`/`idempotency_key`; returns JSON `{ success, 'error-codes', hostname, action, challenge_ts }`; error codes include `timeout-or-duplicate` (token single-use, 300s TTL). **Server-side validation is mandatory** — the widget alone protects nothing (any string can be POSTed). The **secret key must stay server-side**; set reasonable timeouts; validate on every request. Official dummy keys exist for local/CI testing (site `1x00000000000000000000AA` always-passes, secret `1x0000000000000000000000000000000AA` always-passes; production keys reject dummy tokens and vice-versa).
- **Contact-form email relay pattern:** the relay's **`From` must be the verified SES identity**, NOT the visitor's address (spoofing the visitor in `From` fails SPF/DKIM alignment and tanks deliverability); the visitor's address goes in **`Reply-To`** so the owner replies straight to them. This is the standard transactional contact-relay pattern.
- **Honeypot hiding technique** (verified against current honeypot guides): prefer **off-screen positioning** (`position:absolute; left:-9999px`) over `display:none` (which sophisticated bots detect and skip) and over the `.visually-hidden` clip pattern; combine with a **non-real field name** (browsers autofill "company"/"phone"/"address" — a false positive that silently drops a real message), `autocomplete="off"`, `aria-hidden`, and `tabindex="-1"`.

It is instead a **dedicated `/contact` page** — industry-standard, better for SEO/crawlability, and a real top-nav "Contact" item, rather than burying a form in About. ### The homework (current best practice, verified at implementation time — not from memory)
- **SES v2 attachments:** since **2025-04** the SES v2 `SendEmail` API accepts attachments directly on **`Simple`** content (an `Attachments[]` array of `{ FileName, RawContent, ContentType, ContentDisposition, ContentTransferEncoding }`); the AWS SDK base64-encodes `RawContent` for the wire automatically. ## On-demand CloudFront invalidation — the proper edge-freshness fix (built + verified live on staging 2026-08-04)

Closes "Immediate next steps" item 3b (⭐ HIGH). Before this, OpenNext's automatic CDN invalidation was a dummy no-op, so a CMS publish refreshed the S3/ISR origin but CloudFront kept serving stale HTML until `s-maxage`; the interim workaround pinned every content page to `revalidate=10`. This slice implements the real fix — purge CloudFront on demand when content changes — and unwinds the workaround (`revalidate` back to 300).

### The homework (current best practice, verified at implementation time)
- **OpenNext (verified in its docs):** automatic CDN invalidation is off by default; 3.4+ ships a built-in `cloudfront` override that fires on `revalidatePath`/`revalidateTag`, but it needs a `CLOUDFRONT_DISTRIBUTION_ID` env var on the server. SST's own Nextjs `invalidation` prop only fires on `sst deploy`, not on CMS edits — so neither built-in path solves "purge when the admin publishes."
- **SST #5990 (the blocker, verified still open):** you cannot pass the distribution id to the server function in one pass — the function would depend on the distribution's id while the distribution depends on the function URL as its origin (a Pulumi cycle).
- **Chosen approach:** write the id to an SSM parameter created AFTER the Nextjs component (parameter depends on the distribution, not vice-versa ⇒ no cycle), pass only the parameter NAME (a static string) to the function, and read the id at runtime. Standard AWS pattern (Parameter Store for runtime config); keeps the engine isolated behind one module.

### What was built (files in this slice)
- **NEW `src/lib/cdn/invalidate.ts`** — `invalidateCdn(paths=['/*'])`: resolves the distribution id from the SSM parameter named by `CDN_DISTRIBUTION_ID_PARAM` (cached per warm instance; a failed/empty lookup is NOT cached, so it retries next edit), calls `CreateInvalidation('/*')`, is time-boxed by a 5s AbortController, and **never throws** (a purge failure must not roll back the admin save — the ISR window is the safety net). Silent no-op when the env var is unset. Test seam `__setCdnImplsForTests` (mirrors the translation provider). New deps `@aws-sdk/client-cloudfront` + `@aws-sdk/client-ssm`.
- **`src/lib/revalidate.ts`** — extracted the revalidate + purge work into an exported `revalidatePublicSiteNow()` (unconditional) that both the standalone hook (flag-gated) and the translation hook call. `invalidateCdn` is a STATIC import (server-only module, like the AWS Translate hook); a dynamic import proved unnecessary and risked OpenNext not bundling it.
- **`src/lib/translation/hook.ts`** — the fix for the latent bug (below): calls `revalidatePublicSiteNow('post-translation')` once at the end and no longer restores `disableRevalidate`.
- **`sst.config.ts`** — `new aws.ssm.Parameter('WebCdnDistributionId', { name: '/bulbau-lu/${$app.stage}/web-cdn-distribution-id', value: web.nodes.cdn!.nodes.distribution.id })` after `web`; `CDN_DISTRIBUTION_ID_PARAM` env + `ssm:GetParameter` (scoped to the param ARN) / `cloudfront:CreateInvalidation` (`arn:aws:cloudfront::*:distribution/*`) runtime permissions on the Web function. Deploy role unchanged.
- **Seven `src/app/[locale]/**/page.tsx`** — `revalidate` 10 → 300.
- **NEW `tests/int/cdnInvalidation.int.spec.ts`** — 10 unit tests (no-op unconfigured, `/*` default, explicit paths, id-null skip, never-throws on SSM/CloudFront error, id caching, retry-on-failed-resolution). `.env`/`.env.example` document `CDN_DISTRIBUTION_ID_PARAM`.

### The latent revalidation bug this exposed (and fixed)
On-demand revalidation had been broken for translated content **since Phase 5**, masked by the 10s window. The translation `afterChange` hook set `req.context.disableRevalidate=true` before its nested FR/DE writes and relied on restoring it so the top-level save's revalidate hook fired. That restore does NOT reach the outer save (proven: every revalidate fire logged `disableRevalidate=true`, never `false`), so the main save's `revalidatePath` AND CDN purge were both skipped. **Fix:** the translation hook leaves the flag set (suppressing the standalone hook for nested + top-level writes) and calls `revalidatePublicSiteNow()` itself exactly once. Robust because it relies on flag *propagation* (works), not *restoration* (didn't). Non-translated saves/deletes still use the standalone hook.

Sandbox: the 10 unit tests pass; changed modules `tsc`-clean (scoped) + eslint-clean; the CloudFront `CreateInvalidation` and SSM `GetParameter` command shapes were checked against the shipped SDK typings. CI: `verify` green after the `fast-uri`/`undici` override fix. **Live on staging (Filip):** a publish now creates an invalidation on `E3FHUL6KW814N6` (`list-invalidations` shows a fresh entry at edit time), the logs show `[revalidate] revalidating public site + purging CDN (post-translation)` → `[cdn] invalidation created…`, and the edit reaches the edge within seconds instead of 5 minutes.

## Phase 5 part 1 — Translation pipeline (AWS Translate auto-translation on save; built + confirmed on staging 2026-08-02)

The biggest remaining feature. CMS content is authored in EN; this slice makes it **auto-translate to FR and DE on every save**, so the FR/DE public pages render real translated content instead of the EN fallback. Built as a clean, engine-agnostic module and confirmed working on staging by Filip (translation appears, saves are fast). It took several iterations to get right — the failure modes are recorded below because a fresh session will benefit from not re-hitting them.

### Engine decision — AWS Translate, NOT DeepL (re-verified against 2026 pricing)
TECHSPEC §6.7 named DeepL ("best FR/DE quality; free 500K/mo"). **That free tier is gone** — verified against DeepL's current pricing: DeepL API Free/Pro can no longer be purchased; new accounts get a **one-time 1M-character Developer allowance**, then paid Growth. For an ongoing (small but recurring) need that's the wrong fit. Chose **AWS Translate** on cost + architecture (own research, verified on the AWS pricing page, updated 2026-06-08):
- **Cost:** $15 per million characters, pay-as-you-go, **plus 2M chars/month free for the first 12 months**. This site's entire content is well under 100K chars ⇒ a full re-translation is ~$1.50, edits are fractions of a cent, and it's **$0 for the first year**. No base fee.
- **Architecture (the deciding factor):** the app already runs entirely on AWS. Translate authenticates via the **Lambda execution role (IAM)** — so **no new API-key secret** to manage/rotate, and **no new external sub-processor** (it *removes* DeepL from the DPA/sub-processor list). The deploy policy gained `translate:TranslateText` on `resources:['*']` (Translate has no resource ARNs). One credential model — the Well-Architected choice.
- **Capability:** EN→FR/DE with a **FORMAL** register (verified AWS supports Formality for both fr and de — the right business tone). Quality is a notch below DeepL's FR/DE edge, but any imperfect string is correctable via a manual per-locale override.
- The engine is isolated behind `src/lib/translation/provider.ts`'s small interface (`translateTexts`/`buildTranslationMap`/`isTranslationConfigured`); swapping providers again would touch only that one file. New dep: `@aws-sdk/client-translate`.

### Architecture — a synchronous `afterChange` hook (deliberate, researched deviation from §6.7's Jobs Queue)
The spec proposed Payload's Jobs Queue + a scheduled Lambda. Verified reasons that's wrong here: Payload's `autoRun` worker is **explicitly not for serverless**; Next's `after()` (post-response work) is **unsupported on OpenNext AWS** (verified in OpenNext issues); and a true async worker would need Payload bundled into a **second Lambda** — disproportionate for a single-admin, low-volume CMS, and the queue-on-cron alternative breaks "immediately live in all three languages." So translation runs **synchronously in the collection/global `afterChange` hook** — migration-free, and the translation is present the instant the save completes. If write volume ever grows, the async-worker upgrade is the documented path.

**Payload's `afterChange` runs INSIDE the save transaction** (verified in Payload docs: a throw/timeout in the hook rolls the whole save back). That single fact drove every safeguard:
- **Pacing** (`src/lib/translation/provider.ts`): AWS Translate real-time `TranslateText` is **one string per call**, default quota **20 req/s**. Firing many concurrently bursts past the quota → throttling → the SDK's exponential-backoff retries balloon a document to tens of seconds. So a tiny **token bucket paces call starts at ~16/s** (no throttle → no backoff → steady, predictable throughput), plus `maxAttempts: 2`.
- **Hard 12s in-save deadline** (`src/lib/translation/hook.ts`): a shared `AbortController` aborts all AWS calls at 12s. Combined with an explicit **`server.timeout: '30 seconds'`** on the Web Lambda (`sst.config.ts` — it had none, so it used OpenNext's short default), the function can never be killed mid-transaction ⇒ **no rollback**. If the deadline is hit (only pathological content), the pass is abandoned; content still commits and the self-healing pass fills the rest next save.
- **Never throws:** each locale is wrapped in try/catch, so a provider outage or deadline just logs a warning; the EN save always commits (FR/DE fall back to EN).
- **Sequential locales, not parallel:** FR then DE — they share the save's single Postgres transaction, which can't run concurrent queries.
- **Bulletproof recursion guard:** the hook's own FR/DE writes would re-trigger `afterChange`. The guard **MUTATES `req.context.skipAutoTranslate` = true** (and shares `req` with the nested writes) rather than passing the per-call `context` argument, because Payload's handling of `context` *when a `req` is also passed* is ambiguous — and a guard that didn't reach the nested hook made the FR/DE writes re-translate on every level (each level sees FR≠EN as a "change"), looping until the Lambda timeout. **This was the "3-minute create" bug.** Both flags (`skipAutoTranslate`, `disableRevalidate`) are captured and restored in `finally` so the original save still revalidates once and a multi-doc request still works.
- **Self-healing + override-safe field selection** (`translateDocument.ts`): a field is (re)translated iff its EN source **changed** OR the target is still the untranslated **EN fallback** (`base` deep-equals `source`). So content that predates the pipeline, a field left untouched in an edit, or a field a prior run failed on all get filled on the next save — while a real translation or a **manual per-locale override** (both differ from the source) are **left untouched**. This is what lets a fresh translation be filled by simply re-saving, and what makes overrides safe. Requires the **DEPTH CONTRACT**: the hook reads both the EN source and the target `base` at **depth 0** so the whole-field deep-compare isn't fooled by a relationship/upload populated at a deeper depth (e.g. the service `card`'s image id).

### The CloudFront cache gotcha (found + worked around here; PROPERLY FIXED 2026-08-04 — see the "On-demand CloudFront invalidation" section above)
> **Update 2026-08-04:** the "proper fix" below is now built and live. Content pages are back to `revalidate = 300`, and a `/*` CloudFront invalidation fires per edit. The `revalidate = 10` / `staleTimes` / `prefetch={false}` details below are the historical interim workaround (the client-side `staleTimes`/`prefetch` bits were left in place as harmless polish; the `revalidate=10` was reverted to 300).

Symptom: after a publish, hard refresh showed old content for **>1 minute**. Root cause (verified in OpenNext docs): **OpenNext's automatic CDN invalidation is a dummy no-op by default** — `revalidatePath` refreshes the S3 origin cache but **CloudFront keeps serving its cached HTML until `s-maxage` expires** (the pages were `revalidate = 300` → up to 5 min). `revalidatePath` alone can't fix it because CloudFront is never told to purge. Also confirmed the layout-form of `revalidatePath` does **not** reliably cascade into nested **dynamic** routes on OpenNext, so `revalidate.ts` now revalidates **each content page pattern explicitly by `'page'` type** (`/[locale]`, `/[locale]/services/[slug]`, projects/about/careers/legal/privacy, `/sitemap.xml`).

- **The PROPER fix (HIGH-priority next step):** on-demand **CloudFront invalidation** (a single `/*` wildcard per change is ~free — 1,000 free paths/mo) would give truly-instant edge freshness *and* let the cache window go back up (cheaper). It's blocked only by SST not cleanly exposing the CloudFront **distribution ID** to the app — a known circular-dependency (SST issue #5990); the indirect wiring (e.g. an SSM parameter the function reads at runtime, + `cloudfront:CreateInvalidation`) needs care and should be built with the deploy tested step-by-step. See "Immediate next steps".

### Iteration history (failure modes a fresh session should not re-introduce)

5. **"3-minute create"** — recursion: the FR/DE writes re-triggered translation because the guard's flag didn't reach the nested hook. Fixed by mutating `req.context` (bulletproof) + reverting parallel→sequential (shared transaction).

## Foundational IaC layer — Route 53 zone, Neon, deploy role, budgets/alarms (built + APPLIED 2026-07-31)

Triggered by a fresh, evidence-based project review (prompted by catching that the hosted zone was about to be created by hand). The review confirmed the app itself is healthy (deps current, CI strong, no committed secrets — see the "Current state" callout items 6–7) but that **IaC coverage of long-lived/stateful resources was the systematic weak spot**: the same class of gap in three places. This slice closes it by introducing `infra/terraform/`.

### The gap it closes
- **The hosted zone** would otherwise be a manual console click (not IaC).
- **Neon** (the database) was provisioned by hand — and `sst.config.ts` *claimed* Terraform already managed it (a doc-vs-reality lie; there were zero `.tf` files in the repo, verified by glob).
- **The deploy IAM policy** is hand-pushed with `aws iam put-role-policy`, so `infra/aws/github-actions-deploy-policy.json` could silently drift from the live role ("file ≠ live", a trap that bit twice during the account migration).
- **No observability/budget**: "if the app breaks or overspends, nothing tells you."

### The homework (current best practice, re-researched at implementation time)
- **State backend:** S3 with **native locking** (`use_lockfile = true`, Terraform ≥ 1.11) — **no DynamoDB** (that approach is deprecated in 2026 and slated for removal). Cheaper, fewer moving parts.
- **Nameserver stability:** a **reusable delegation set** (`aws_route53_delegation_set`) feeding the zone — fixed, free, four nameservers so the zone can be destroyed/recreated (the "$0 off" mode) without ever re-delegating at EuroDNS.

- **IAM:** bring the existing role under Terraform via **import**, sourcing the trust + permission JSON from the committed `infra/aws/*.json` via `file()` so those files become the single source of truth (`terraform plan` = drift detector).
- **Cost/observability:** AWS Budgets (us-east-1, direct-email notifications — no SNS needed) + CloudWatch `AWS/Lambda` alarms → SNS email.

## AWS account migration + dependency/CI hardening (2026-07-22 → 2026-07-27)

The app was moved out of the shared `acc-test` account into its own dedicated AWS account, and a round of dependency/CI-audit hardening landed alongside (forced by newly-published advisories tripping the gate mid-migration). This section is the authoritative record for a fresh session.

### Why migrate

The app was sharing account `176971015975` (`acc-test`) with an **unrelated online shop**. Two concrete problems: (1) **Lambda concurrent-executions quota is per-account** and defaulted to **10** — this app alone deploys ~5 OpenNext Lambdas + a warm instance + the Pdf Lambda, so a burst could throttle *both* businesses; (2) **blast radius** — an IAM slip or runaway in one app could reach the other. AWS's own multi-account guidance says unrelated workloads belong in separate accounts. So a new **`service-calculator-production` account (`847321857537`)** was created (via the OrgFormation repo, under `OU-Production`, with baseline + region-control SCPs — see that repo).

### How the migration was done (the mental model: redeploy fresh, don't "move")

Everything AWS-side is IaC (SST) or a one-time bootstrap, so migration = **re-bootstrap the new account → deploy fresh there → move the two stateful things → verify → `sst remove` the old**. Only two things hold state a fresh deploy won't recreate: **Neon** (external to AWS — reused as-is, so all data came along by just pointing at the same connection string) and **S3 media** (copied old→new before teardown). Stage kept as **`staging`** (least change — the existing `deploy-staging` CI job just needed its role ARN + DB secret repointed; avoids the `production` stage's `protect`/`retain` behaviour). Secrets re-set in the new account with the **same values** (critical: reusing `TotpEncryptionKey` verbatim so existing 2FA enrolments stay decryptable).

### Deploy-role permission gaps this surfaced (and fixed) — worth a fresh session knowing

The old account's stack was originally **bootstrapped by an admin**, so its restricted CI deploy role never had to *create* most resources. In the new account the CI role creates **everything** from scratch, which exposed real gaps in `infra/aws/github-actions-deploy-policy.json` — each the same shape (a **global service** with no region, so the broad `eu-central-1`-scoped statement never covered it):

- **`iam:CreateRole` on the OpenNext internal roles.** SST's `Nextjs` component names some roles with a *stage-truncated* prefix (`stagi-WebRevalidation…`), not `bulbau-lu-staging-*`, so the prefix-scoped `ManageAppIamRoles` denied them. **Fix:** widened `ManageAppIamRoles` resource to `role/*` (this account is single-app, so that's effectively "the app's roles"), **plus a new `ProtectCriticalRoles` Deny** guarding the SSO / `OrganizationAccountAccessRole` / the deploy role itself from being modified or deleted — so the broadened Allow can't be abused. Prefix-matching was abandoned as unworkable (truncation is unpredictable).

## Public `/api/quote` rate limit + payload cap (built 2026-07-22)

Another **genuinely-missed, fully in-repo, fully CI-provable** hardening slice that the prior sessions' "everything remaining is externally gated" conclusion had **overlooked** — the same class of miss as the security-headers slice. Found by an independent review of the one public, unauthenticated endpoint that does *expensive* work: **`POST /api/quote` had no rate limit and no payload cap**, yet every call re-loads the service from Neon **and** invokes the isolated **1600 MB / 60 s Chromium PDF Lambda**. A trivial scripted loop (`while true; curl …`) against it could run up real AWS cost (Lambda-seconds + Neon) or exhaust concurrency — a live **AWS Well-Architected gap across the Security, Cost-Optimization, and Reliability pillars**. The app already had a proven Upstash-backed rate limiter, but it was **TOTP-only**; nothing guarded the far more cost-sensitive public PDF path. Chosen precisely because it needs **no external gate** (the Upstash instance already exists for login; local/CI use the in-memory fallback) and is **provable end-to-end in CI** — unlike the two remaining `<img>`→`next/image` / nonce-CSP items, which are staging-only. **App code + tests only — no schema, no migration, no new dependency, no infra/secret change**; entirely `git revert`-able.

### The homework (current best practice, re-researched at implementation time)

Grounded in fresh research (Next 16 App Router, OpenNext/CloudFront, OWASP), not plan-era assumptions:

- **Client-IP keying must be spoof-resistant behind CloudFront.** The naive "first `X-Forwarded-For` entry" is **client-controlled** — an attacker can prepend arbitrary IPs to rotate past an IP limiter. Behind CloudFront the trustworthy signal is CloudFront's own **`CloudFront-Viewer-Address`** header (set from the TCP connection, un-spoofable via the request chain); the real viewer IP that CloudFront itself appends to `X-Forwarded-For` is the **last** hop, not the first. So `getClientIp` prefers `CloudFront-Viewer-Address` (stripping the `:port`, IPv6-bracket-aware), then falls back to the **last** `X-Forwarded-For` hop, then `x-real-ip`, then a constant fail-safe bucket (an IP-less request is still limited — fail-safe, never fail-open). *Caveat, documented as a follow-up:* `CloudFront-Viewer-Address` only reaches the origin if the CloudFront distribution is configured to forward it; the code degrades gracefully to XFF until then, and even the XFF path stops the common single-IP scripted-loop abuse that is the primary cost risk.
- **App Router route handlers can't declaratively cap body size** (confirmed against the Next docs — `proxyClientMaxBodySize`/`middlewareClientMaxBodySize` exist but not a route-handler `maxRequestBodySize`). So the correct mitigation is an **in-handler `Content-Length` guard** (16 KB — the quote body is a few hundred bytes) plus a **parsed-object field-count cap** (200 fields), both cheap and defensive.
- **Sliding window, reusing the proven limiter.** The existing TOTP limiter's Upstash-`slidingWindow`-or-in-memory design is exactly right; generalizing it (rather than adding a second library) keeps the strict `npm audit --audit-level=high` CI gate clean and the behaviour identical to the already-tested login path. **10 / minute / IP** is generous for a real visitor tweaking inputs and re-downloading a few times, while capping a scripted abuser hard.

### What was built (files in this slice)

- **`src/lib/rateLimit.ts` (new, generic)** — the shared limiter extracted from the TOTP-only one: `checkRateLimit(policy, key)` (Upstash when `UPSTASH_REDIS_REST_URL/TOKEN` are set — one cached `Ratelimit` per policy `prefix`; else the in-memory sliding window, keyed `${prefix}:${key}` so policies never collide), `__resetRateLimitForTests()`, the `RateLimitPolicy` type, and **`getClientIp(request)`** (the CloudFront-aware extraction above).

## HTTP security response headers (built + verified 2026-07-21)

A genuinely **unblocked, fully in-repo, fully CI-provable** launch-hardening slice that the prior sessions' "everything remaining is externally gated" conclusion had **missed**: the app served **zero** HTTP security response headers. A code review of `next.config.ts`, `sst.config.ts`/CloudFront, and `src/proxy.ts` confirmed there was no `Strict-Transport-Security`, `Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`, `frame-ancestors`/`X-Frame-Options`, or `Permissions-Policy` anywhere. For a public site with a 2FA admin panel heading to production, that is a real AWS Well-Architected **Security-pillar** gap (and it feeds Lighthouse's best-practices CSP/HSTS audits). Chosen precisely because it is the one high-value hardening item left that needs **no** external gate (no domain, no SES, no DeepL, no manual AWS/GitHub step) and is provable end-to-end in CI. **App-config + tests only — no schema, no migration, no dependency, no Payload-config/importMap change** (so the schema- and generated-artifact-drift guards stay green); entirely `git revert`-able.

### The homework (current best practice, re-researched at implementation time)

Grounded in the **OWASP Secure Headers Project** + the **Next.js CSP guide** (fetched this session), not the plan-era assumptions:

- **The full "safe scalar" set is unconditionally shippable** and breaks nothing: `Strict-Transport-Security` (OWASP-recommended 2-year `max-age=63072000; includeSubDomains`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: SAMEORIGIN`, `X-XSS-Protection: 0` (OWASP now says *disable* the legacy auditor and rely on CSP), `X-Permitted-Cross-Domain-Policies: none`, `Cross-Origin-Opener-Policy: same-origin`, and a restrictive `Permissions-Policy`.
- **CSP is the one that can break things.** A real XSS-grade CSP locks down `script-src`/`style-src`, which for **Next.js + Payload** requires **per-request nonces** threaded through the response (Next's documented `proxy.ts` nonce pattern). Getting it wrong **silently breaks the Payload admin at runtime with no build-time error** (inline bootstrap script + inline styles) — the exact "no build-time error" failure class TECHSPEC §12 already warns about for the import map. So per this project's **"prove risky things on staging / ratchet, don't guess"** rule, the nonce-based part is a deliberately separate, **report-only-first** follow-up.
- **The CSP directives that need NO nonce are safe to enforce now** and are high-value on their own: `base-uri 'self'` (blocks `<base>` injection), `object-src 'none'` (kills legacy-plugin vectors), `frame-ancestors 'self'` (modern clickjacking defence, superset of `X-Frame-Options`), `form-action 'self'` (forms can only POST to our own origin). Crucially there is **no `default-src`**, so script/style/img/font stay unrestricted and nothing inline breaks.
- **`upgrade-insecure-requests` deliberately omitted** — it would try to upgrade `http://localhost` sub-resources in local `next dev` / the Playwright webServer (both plain HTTP), breaking dev/e2e; CloudFront already redirects http→HTTPS in front of every deployed stage and HSTS enforces it thereafter, so it adds nothing.
- **`next.config` `headers()` over `proxy.ts`** for these: the set is static (no per-request value), so `headers()` is the canonical, cache-friendly, OpenNext-supported home. (If/when the nonce-based `script-src` CSP lands, *that* directive moves to `proxy.ts` for the per-request nonce.)

### What was built (files in this slice)

- **`src/lib/security/headers.ts` (new, pure, dependency-free)** — the single source of truth: the `securityHeaders: {key,value}[]` array + the composed `CONTENT_SECURITY_POLICY` / `PERMISSIONS_POLICY` strings, each with a doc-comment explaining the choice. Imported by both the config and the test so they can never drift.
- **`next.config.ts` (modified)** — an `async headers()` returning `[{ source: '/:path*', headers: securityHeaders }]`, and a **relative** import of the module (`./src/lib/security/headers`, not the `@/` alias, so Next's config loader resolves it without the tsconfig path mapping).
- **`tests/int/securityHeaders.int.spec.ts` (new)** — pure assertions on the exact set/values (all OWASP keys present exactly once, HSTS ≥2yr + `includeSubDomains` + no premature `preload`, the scalars, the CSP contains the four nonce-free directives and **omits** `script-src`/`style-src`/`default-src`/`upgrade-insecure-requests`, the Permissions-Policy disables camera/mic/geolocation/payment). Auto-discovered by vitest's `tests/int/**/*.int.spec.ts` glob — no CI change.
- **`tests/e2e/securityHeaders.e2e.spec.ts` (new)** — proves the **running Next server actually emits** the headers (not just that the module is correct) on a public localized page, `/admin/login`, and the `/api/quote` route. Empty-DB-safe (asserts only response headers), so green on CI's empty Postgres. Auto-discovered by Playwright's `testDir`.

### Decisions worth a fresh session knowing

- **Single-source-of-truth module, asserted by an int test.** Same pattern as the CI drift guards: the config and the test read the *same* array, so a hand-edit to one without the other fails CI.
- **Applied globally (`/:path*`), including `/admin` and `/api`.** None of the chosen headers restrict inline script/style, so the admin is safe; the admin login page *benefits* most from clickjacking protection. `nosniff` is also correct on the JSON/PDF API responses.
- **Enforce-safe CSP now, nonce-based CSP later.** The four nonce-free directives deliver clickjacking/base-injection/plugin/form-exfiltration protection today with zero runtime risk; the `script-src`/`style-src` lockdown is the staging-verifiable, report-only-first Phase 7 follow-up.
- **HSTS without `preload`.** A `*.cloudfront.net` host can't be HSTS-preloaded and `preload` is a hard-to-reverse commitment — add it at launch on the real domain.

### Verification (what was run, and where)

## CI generated-artifact drift guard (built + verified 2026-07-21)

### The gap it closes

Payload has **three** generated-but-committed artifacts. The schema-drift guard now covers migrations (`src/migrations/`). The other two had **no** guard:

- **`src/app/(payload)/admin/importMap.js`** (`generate:importmap`) — the map from admin-component references in the config to their modules. If a collection/field/plugin adds or removes a custom admin component and this isn't regenerated, **the admin panel breaks at RUNTIME with no build-time error** — this exact failure mode is already documented in TECHSPEC §12 ("silently stale otherwise, with no build-time error") and Phase 0's lessons. The repo has real custom components in this map (`FormulaBuilder`, `BeforeDashboardTotpGate`, `TotpSetupView`, `TotpVerifyView`), so it's a live risk, not theoretical — Phase 3 part 2 added `FormulaBuilder` to it.
- **`src/payload-types.ts`** (`generate:types`) — the generated TS types the whole app imports. If stale, code type-checks against a schema that no longer matches (or silently loses type safety on new fields).

Neither `lint`/`typecheck`/`test:int`/`build` fails on a stale copy of either file, so drift could ship unnoticed — the same class of silent gap the schema guard closed for migrations.

### The homework (re-checked against the *installed* source, per the standing rule)

Grounded in `node_modules/payload/dist/bin/index.js` + `generateTypes.js` + `generateImportMap/index.js` (payload@3.86), not just the docs/search results — the "verify assumptions against installed source" rule again earned its keep:

- **Neither command needs a DB.** `index.js` handles `generate:types`/`generate:importmap` by calling `generateTypes(config)` / `generateImportMap(config)` **directly, without `getPayload()`** (unlike `jobs:run`, and even more than `migrate:create`'s `disableDBConnect:true` — these don't init Payload at all). So the guard needs no Postgres service and can't flake on the DB — it sits happily in `verify` alongside the schema guard.
- **Both are idempotent when in sync.** `generateTypes` reads the existing `outputFile`, compiles the schema, and **returns early without writing if the compiled string is byte-identical** to what's on disk. `writeImportMap` does the same (trim-compares current vs. new, skips the write if equal). So on an in-sync tree neither file is touched ⇒ **no false-positive diff**.
- **No formatting fight.** `payload-types.ts` is in eslint's `ignores` and there is no prettier CI step, so the committed files ARE the raw generator output — regenerating with the pinned `payload@3.86.0` reproduces them exactly. (If a prettier `--check` step is ever added, exclude both files, or the guard and prettier would disagree.)
- **Output paths confirmed:** `typescript.outputFile: path.resolve(dirname,'payload-types.ts')` ⇒ `src/payload-types.ts`; `admin.importMap.baseDir: path.resolve(dirname)` with the default `importMapFile` ⇒ `src/app/(payload)/admin/importMap.js`. Both match the committed, git-tracked paths.
- **Community context:** payloadcms/payload discussion #10978 (the "replicate Django `makemigrations --check`" thread) explicitly wished for this generate:types/importmap check as the migration check's sibling; there's no built-in `--check`, so the blessed pattern is regenerate-then-`git diff`.

### What was built (this slice)

- **`.github/workflows/ci.yml`** — one new step in `verify`, **immediately after the schema-drift guard, before the content-seed/build steps** (groups the three "generated artifact in sync with config" gates; leaves the working tree clean for the seed):
  ```
  npm run generate:types
  npm run generate:importmap
  drift="$(git status --porcelain -- src/payload-types.ts 'src/app/(payload)/admin/importMap.js')"
  if [ -n "$drift" ]; then  → ::error (+ print `git diff` of the stale files) + exit 1  else  ✅  fi
  ```
  Detection is **`git status --porcelain` scoped to the two exact paths** (version-independent — doesn't depend on any CLI log wording), and the actual `git diff` is printed on failure so the fix is self-evident. A generate command that *errors* (config problem) fails the step on its own (default `bash -e`), which is also correct.

- **Default price path on purpose.** No `formula`, so the calculator exercises the Σ-signed-`unitPrice×value` path (the common case). The custom-formula path is already covered exhaustively by the pure unit tests, so re-covering it here would add nothing.
- **Skip-on-404 keeps local runs tolerant.** The new axe/e2e tests skip when the sample page 404s (a local empty DB), so they're deterministic in CI (seeded) without forcing every developer to seed first.

### The bug found during testing (and fixed) — worth a fresh session knowing

- **Floating promise vs. `payload run` → a silent no-op.** The first runner did `seedSampleContent().then(() => process.exit(0)).catch(...)` (a *floating* promise, avoided top-level await over a since-disproven tsc worry). `payload run` only waits for the module's **synchronous** top level to finish, then exits — abandoning the floating promise **before Payload even booted**. Symptom: `npm run seed:ci` printed **nothing at all** (no Payload boot logs, no `[seed]` line, no error) and wrote no data. **Fix:** a **top-level `await seedSampleContent()`** in the runner (which is exactly what the Payload docs' seed example uses; `module: esnext` supports TLA, so `tsc` is fine). **Lesson:** with `payload run` (and standalone ESM scripts generally), the entry must `await` its async work at the top level — a fire-and-forget promise is killed on module-eval completion, and the failure is invisible (no output), not a stack trace.

## CI schema-drift guard (built + verified 2026-07-21)

The migration-safety hardening that Phase 1.5 flagged as "still not done" and "Immediate next steps" carried as item 4, finally closed. Chosen as this slice because **every remaining *feature* is externally gated** (Phase 4 part 2 needs the `bulbau.lu` domain + a verified SES identity; Phase 5 needs a DeepL key; Phase 6 needs the domain + the client's real legal details) — so a slice that can be *implemented and fully proven end-to-end* has to be an in-repo, CI-provable one, and this is the highest-value such item left: it protects the migrate→deploy pipeline, is a direct AWS Well-Architected **Operational-Excellence** hardening step, and is entirely `git revert`-able. **CI-config only — no app code, no schema, no migration, no dependency.**

### The gap it closes

The `verify` job runs with Drizzle **`push` ON** (`NODE_ENV` unset ⇒ `src/payload.config.ts`'s `push: NODE_ENV !== 'production'` is true), so it auto-syncs the schema to the config on boot and therefore **passes happily on an un-migrated schema change** — a new field/collection that nobody ran `migrate:create` for is invisible to `lint`/`typecheck`/`test:int`. Then `deploy-staging`'s `payload migrate` runs with **`push` OFF** and applies **nothing**, shipping code whose expected columns/tables were never created on staging → runtime errors or a broken deploy. Nothing in CI caught this before; the drift was only ever found by hand (Phase 2b's migration was verified drift-free manually with exactly the command this slice automates).

### The homework (re-checked at implementation time, per the standing rule)

The community-blessed pattern (payloadcms/payload discussion #10978 — the "replicate Django `makemigrations --check`" thread) is `payload migrate:create --skip-empty` + detect whether a file appeared. **Verified against the *installed* `payload@3.86.0` source, not the search results** (the standing "verify assumptions against installed source" rule earned its keep here):

- **There is NO `--check` flag in 3.86.** A web-search summary claimed one exists; `node_modules/payload/dist/bin/migrate.js` only recognizes `skipEmpty` and `forceAcceptWarning`. Using `--check` would have been a silent no-op. (An official non-interactive flag is still only a feature request — issue #14941.)
- **`migrate:create` needs no DB and causes no push.** `migrate.js` inits Payload with **`disableDBConnect: true`** (for the `migrate:create` command specifically) and `disableOnInit: true`, so the check never connects to Postgres and never pushes — it purely diffs the schema built from the config against the snapshot (`.json`) of the latest committed migration (`@payloadcms/drizzle/.../buildCreateMigration.js`).
- **`--skip-empty` behaviour, exactly:** in `buildCreateMigration.js`, when the up/down SQL is empty it `process.exit(0)`s **without** writing a file or prompting; when there ARE changes it writes `<ts>_<name>.{ts,json}` into the migration dir and logs `Migration created at …`. So no-drift = clean exit + no file; drift = a new file.
- **The one hang risk:** an *ambiguous* enum/column **rename** drops drizzle-kit into an interactive TUI ("Is X created or renamed?") that `--skip-empty` does **not** bypass (discussion #10978, mrobinsonFS Sep 2025). Neutralized with `</dev/null` (the prompt reads EOF and the command exits non-zero) + a `timeout` (belt-and-suspenders against any hang).

### What was built (this slice)

- **`.github/workflows/ci.yml`** — one new step in `verify`, **after `test:int`, before the content-seed step** (schema is in a known state; the seed/build come after and are unaffected):
  ```
  timeout 180s npm run migrate:create -- ci_drift_check --skip-empty </dev/null 2>&1 | tee drift-check.log
  status=${PIPESTATUS[0]}
  drift="$(git status --porcelain src/migrations)"
  if [ -n "$drift" ] || [ "$status" -ne 0 ]; then  → ::error + exit 1  else  ✅  fi
  ```
  Detection is by **`git status --porcelain src/migrations`** (version-independent — does not depend on the CLI's log wording), scoped to `src/migrations` so nothing else in the working tree can confuse it. A fixed name (`ci_drift_check`) labels any file that *would* be written; it's never committed (the job fails first). `${PIPESTATUS[0]}` captures `migrate:create`'s exit code, not `tee`'s.

### Decisions worth a fresh session knowing

- **git-status detection, not log-string grep.** The busbyk snippet in #10978 greps stdout for "Migration created at"; a `git status` check on `src/migrations` is more robust (survives a log-wording change between Payload versions) and also catches a modified snapshot, not just a new file.
- **Placed in `verify`, runs on every PR and push.** It's a correctness gate, so it belongs where lint/typecheck/test already gate — not only on deploy. It needs no DB (see homework), so it costs nothing extra and can't flake on the Postgres service.
- **Ambiguous rename ⇒ fail, by design.** A rename genuinely needs a hand-authored migration (drizzle can't infer intent), so treating the non-zero exit as drift is correct, not a false positive.

### Verification (what was run, and where)

Same standing rule (the sandbox can't run this project's real toolchain — the `payload` CLI needs the Linux esbuild/tsx binary the Windows-mounted `node_modules` doesn't have, and the config transitively imports next-intl → `next/server`; **CI / Filip's machine is the authority**). **In-sandbox:** the ci.yml re-parses as valid YAML with the step correctly ordered after `test:int`; the step's shell script passes `bash -n`; the detection core was simulated in a throwaway git repo across all four cases (no-drift→pass; file-written→fail; non-zero-exit→fail; `PIPESTATUS[0]` captures the right exit code); and the whole design was grounded line-by-line in the installed `payload@3.86` source (above). **On Filip's machine (2026-07-21):** **both directions confirmed** — a clean tree exits with no file (guard passes), and an injected throwaway field makes `migrate:create` write a migration that the guard detects (guard fails), reverted cleanly afterward. **Green in CI** on the normal in-sync tree (the guard logs `✅ No schema drift`).

### Not done in this slice (so a fresh session doesn't assume otherwise)

- ~~**`generate:types` / `generate:importmap` drift checks.** #10978 also wished for these (fail CI if the committed `payload-types.ts` / `importMap.js` is stale). ## Phase 4, part 1 — PDF quote generation + Download (built + verified 2026-07-20)

The first slice of Phase 4: on-demand PDF quote generation with the **Download** path. Same "prove the risky foundation first, then the rest" split used throughout — **Send-to-Email is deliberately part 2**, because it needs a verified SES sending identity, which needed the `bulbau.lu` domain. *(Update 2026-07-31: that domain + the production stage are now LIVE, so the gate is cleared — Phase 4b is the next feature slice.)* That was the same class of external gate the legal pages sit behind, so splitting it kept this slice's testing guide trustworthy. **Migration-free** (no schema change).

### The engineering decisions (homework — worth a fresh session knowing)

TECHSPEC §3/§6.5 originally named **"Playwright + `@sparticuz/chromium-min`"**. Re-researched at implementation time (the standing rule that "current best practices" are re-checked, not trusted from when the plan was written), the built reality — and why it diverges — is:

- **`puppeteer-core` + the full `@sparticuz/chromium` (not `-min`), on an x86_64 function.** The npm `@sparticuz/chromium` package **ships x64 binaries only**; arm64 support (since Chromium v135) exists **only** as a Lambda-layer zip or a self-hosted remote *pack tar* that the `-min` package downloads at cold start. Using `-min` + a remote pack would mean versioning and hosting an extra artifact and paying a cold-start download — more moving parts, against the "periodic-maintenance-only" goal. So the PDF function is **x86_64 with the Chromium binary bundled in the function** (self-contained, nothing fetched at runtime). The main `Web` function stays **arm64** — the two are isolated (which is exactly why TECHSPEC §13 wants the split), so the architecture mismatch is irrelevant, and the cost delta on a rarely-invoked pay-per-call function is negligible. Puppeteer vs Playwright: either drives headless Chromium fine for `setContent`→`pdf`; `puppeteer-core` is the pairing `@sparticuz/chromium`'s own docs target, so it was chosen.
- **The PDF function is a *dumb, stateless HTML→PDF renderer* with no Payload and no DB access.** All business logic (pricing via `src/lib/pricing/`, i18n, company data, the §7 contact state) lives in the main app, which assembles finished HTML and passes `{ html }` to the function; the function only launches Chromium and prints. This matches §13's least-privilege intent ("the PDF function has SES but no database access") and keeps the risky Chromium bundle entirely out of the hot-path app function.
- **The route lives at `src/app/api/quote/route.ts`** (outside the `[locale]` segment — locale travels in the POST body), so next-intl's middleware never rewrites it and it isn't touched by the `/admin` proxy (both exclude `/api`). It coexists with Payload's `(payload)/api/[...slug]` catch-all — a static `/api/quote` outranks the catch-all (confirmed by `build`).

### The IAM deploy-role fix (blocks the staging deploy — needs a manual apply) — ✅ APPLIED 2026-07-21

## Phase 3, part 1 — live price calculator + shared evaluator (built + verified 2026-07-19)

The first user-visible slice of Phase 3: the public **real-time price calculator**, replacing the Phase 2 static/disabled preview. Deliberately bounded to **the shared pricing evaluator + the public calculator**, leaving the admin **visual Calculator Field/Formula Builder** (the non-technical authoring UI, TECHSPEC §6.4) to **Phase 3 part 2** — the same "prove the risky shared foundation first, then the authoring UI" split used for Phase 2. Rationale: the novel engineering (a safe evaluator shared by client + server, the §7 edge cases, the real-time UX) all lives in the evaluator + public component; once proven against hand-authored `formula` JSON, the visual builder is a self-contained admin component that emits that same JSON. **Migration-free** — the `calculatorFields` array + `formula` JSON have existed since Phase 1.

### The engine decision (homework — worth a fresh session knowing)

TECHSPEC §5/§6.3 named `json-logic-js` "(or equivalent safe evaluator)". Re-researched at implementation time (the standing rule that "current best practices" are re-checked, not trusted from when the plan was written): **`json-logic-js` is effectively unmaintained** (no npm release in 12+ months) — a liability against the "stay-current / periodic-maintenance-only" goal. Its maintained successor is **`json-logic-engine`** (MIT, TS-native, ESM+CJS, ~5× faster, v5.0.7). **Decision: keep JSONLogic as the stored/interchange format** (portable, library-agnostic, exactly what the part-2 visual builder will emit) **but evaluate it with a ~50-line zero-dependency in-house arithmetic-subset interpreter** rather than adding either library. Why: the pricing domain is tiny and closed (`var`, `+ − × ÷`, `min`, `max`); owning the evaluator gives full, unit-tested control over the money-math edge cases that actually matter (division by zero, NaN/Infinity, the §7 non-positive-total rule), adds **zero supply-chain surface** — keeping the strict `npm audit --audit-level=high` CI gate clean (recall the `tmp`/lhci episode, where one added dev tool breached that gate) — and involves **no lock-in**: because the on-disk format is standard JSONLogic, swapping in `json-logic-engine` later (if operator needs ever outgrow arithmetic) is a drop-in with **no data migration**. This is the same "custom because the domain is small, well-understood, and we want control" reasoning used for the TOTP crypto.

### What was built (files in this slice)

- **`src/lib/pricing/jsonlogic.ts` (new)** — the safe interpreter. `evaluateJsonLogic(rule, data)` over a closed operator set (`var` with default; `+ − × ÷`; unary `−`; `min`/`max`; nesting for order-of-operations). Never `eval`/`new Function`; an unknown operator or malformed rule **throws** (callers treat a throw as "can't price it"). `isUsableFormula()` distinguishes a real formula from `{}`/`null`/absent. Exports the `JsonLogic`/`LogicData` types.

### Decisions worth a fresh session knowing

- **Two price paths, mutually exclusive for the total.** Default (no formula) = Σ signed `unitPrice × value` — covers the common service with no formula to author, and matches the field-level model in FUNCTIONALITY §5.3. The breakdown shows per-field contributions in the default path (they sum to the total) and entered values under a formula ("where applicable", §4).
- **Required-field gating over always-live.** An "estimate" that silently treats unfilled required inputs as 0 invites false trust; gating on **required only** (not all fields) keeps it responsive (optional fields still default to 0 and update instantly). Hard, blocking validation (format errors, etc.) belongs at PDF-generation time (Phase 4). **0 is a value, blank is not.**

- **Currency is locale-formatted EUR** (`€1,234.50` in EN, `1.234,50 €` in FR/DE), not a hardcoded symbol — correct per-locale placement for the trilingual site.

## Phase 3, part 2 — admin visual Formula Builder + live preview (built + verified 2026-07-20)

The authoring counterpart to part 1: the **non-technical UI that produces** the `formula` part 1 already evaluates. Same "prove the risky shared foundation first, then the authoring UI" split used for Phase 2 and Phase 3 part 1. **Migration-free** — the `calculatorFields` array + `formula` JSON have existed since Phase 1, and this slice changes no schema (only admin-side UI + a pure lib + tests).

### Scoping decision (worth a fresh session knowing)

TECHSPEC §6.4 / FUNCTIONALITY §5.3 describe two things: a **Calculator Field Builder** and a **Formula Builder**. On review, the **field builder is already met by the native Payload `calculatorFields` array** — it gives label / type / options / unit price / +/− sign / required / drag-reorder as first-class field types with zero custom code, which is exactly §5.3's field-builder list. So the genuinely un-built, novel piece is the **Formula Builder + live preview**, and that is what this slice delivers. (Re-implementing the array editor as a custom component would only add risk and duplicate native behaviour.) This is the same "build the risky/novel part, reuse the platform for the rest" judgment used throughout.

### The core design decision: the builder is a *view* over canonical JSONLogic

The stored `formula` value **stays plain JSONLogic** (never the builder's own model). Rationale: the shared evaluator (`src/lib/pricing/`), the public `ServiceCalculator`, and (Phase 4) the PDF all read `formula` as JSONLogic — storing the builder's model there would break all three and force a data migration. So the builder **compiles its structured model → JSONLogic on every edit** (`setValue`) and **parses JSONLogic → model on load**. Anything the builder can produce round-trips losslessly; anything hand-authored outside its canonical shape (e.g. `min`/`max`, division) is detected (`parseFormula` returns `null`) and shown in a **raw-JSON fallback editor** — nothing is ever locked out. This is why the whole compile/parse core is a **pure module** (no React/DB), unit-testable in-sandbox and shared verbatim by the component and the tests.

### What was built (files in this slice)

- **`src/lib/pricing/formulaBuilder.ts` (new, pure)** — the builder model (`BuilderFormula` = ordered `terms[]` + `adjustments[]`) and the two conversions: `compileFormula(model)` → `JsonLogic | null` (null when empty ⇒ the pricing engine's default per-field summation path) and `parseFormula(rule)` → `BuilderFormula | null` (null ⇒ not builder-canonical ⇒ raw fallback). Terms are field (`{var} × ±multiplier`), fixed cost (`±number`), or one-level group (`(Σ members) × factor`, factor a constant or a field, optionally negated). Adjustments are percentages compiled as `× (1 ± p/100)` and peeled back on parse (VAT = `×1.1`, discount = `×0.9`). Emits **only** the operators the evaluator supports (`var`, `+`, `*`); `min`/`max`/`−`/`÷` stay available to raw-JSON authors but aren't surfaced (kept focused on §5.3's requirements).
- **`src/components/admin/FormulaBuilder.tsx` (new, `'use client'`)** — the custom field mounted on `Services.formula` via `admin.components.Field`. Reads the sibling `calculatorFields` live from form state (`useAllFormFields` + `reduceFieldsToValues`) so field dropdowns/preview update as the operator edits fields; edits the value via `useField`; term/group/adjustment editors with add/remove/reorder (up/down, no dnd lib — zero new deps); an **"Edit raw JSON" ⇄ "Use visual builder"** toggle (switching to the builder from a non-canonical rule warns before replacing); and a **live preview** that runs the exact same `computePrice()` the public page uses.
- **`src/components/admin/FormulaBuilder.scss` (new)** — styled with Payload's `--theme-*` variables so it adapts to light/dark automatically.
- **`src/collections/Services.ts` (modified)** — the `formula` field gains `admin.components.Field: '/components/admin/FormulaBuilder#FormulaBuilder'` and a reworded description.
- **`src/app/(payload)/admin/importMap.js` (modified)** — registered the component (Payload regenerates this at startup / `generate:importmap`; the committed entry is kept correct so it's never stale).
- **`tests/int/publicSite.int.spec.ts` (modified)** — 8 new pure tests: empty→null, field/fixed/mixed round-trips, VAT `×1.1` + discount `×0.9`, adjustment-order preservation, group round-trips, non-canonical→null, and one that **evaluates the compiled JSONLogic through the real `evaluateJsonLogic`** to prove preview == production at the arithmetic layer.

### Decisions worth a fresh session knowing

- **Admin UI is English-only** (like the existing TOTP views), so the trilingual next-intl catalogs were untouched — the **109/109/109 key parity holds**. The Payload admin is an owner-facing surface; the public trilingual site is unaffected.
- **Percentage adjustments cover VAT/discount without a new operator** — `× (1 ± p/100)` uses only `*`, so the evaluator's closed operator set was sufficient and **no evaluator change (and no migration) was needed**. Confirmed before building.
- **Live preview mirrors the public required-field gating exactly** — after Filip flagged it in manual testing, the preview now withholds the total and shows "fill the required fields" until every required *number* field has a value (an explicit 0 counts as filled; dropdowns/toggles always carry a value). This preserves "preview == production" — the whole point of the shared module.
- **Groups are one level deep** (`(A + B) × C`), matching §5.3's example, kept shallow for a non-technical UI; deeper nesting isn't a requirement and would only be reachable (and still evaluable) via the raw-JSON fallback.

### Issues found during testing (and fixed) — worth a fresh session knowing

1. **Emptied rich-text ≠ null — the disclaimer fallback bug.** Clearing a service's `disclaimer` in the admin doesn't store `null`; Lexical stores an *empty document* (`{ root: { children: [empty paragraph] } }`), a truthy object. So `service.disclaimer ? …` stayed true and the page rendered an empty `<RichText>` instead of falling back to the default notice. **Fix:** gate on real text — `hasOwnDisclaimer = !!disclaimer && lexicalToPlainText(disclaimer).trim().length > 0`. **General lesson:** never test a Payload rich-text field for presence with a truthiness check; an emptied field is a non-empty object. 2. **`push` ≠ `migrate` — the local backfill gotcha (not a bug).** After deleting a service locally, a *pre-existing* project lost its label. New/edited projects are fine (the hook), and **on staging this doesn't happen** because CI runs `payload migrate` (backfill included). ## Phase 1, part 1 — TOTP 2FA (built 2026-07-06)

Payload has no native 2FA, so this is custom code layered on top of Payload's own email/password auth, per `docs/TECHSPEC.md` §6.6. `docs/FUNCTIONALITY.md` §5.1 treats 2FA as **mandatory, not optional**.

### What was built (files in this slice)

- `src/lib/totp/` — the crypto/OTP toolkit, all Node-runtime:
  - `keys.ts` — one root secret (`TOTP_ENCRYPTION_KEY`, separate from `PAYLOAD_SECRET` for key separation) → two HKDF-derived subkeys (one for AES-256-GCM encryption, one for HMAC signing).
  - `crypto.ts` — AES-256-GCM encrypt/decrypt of the TOTP secret at rest (`iv:authTag:ciphertext`, base64).
  - `otp.ts` — `otplib` wrappers (SHA-1/6-digit/30s defaults, matching mainstream authenticator apps); `epochTolerance: 30` (±1 window) and `afterTimeStep` replay protection.
  - `stepUpToken.ts` — plain HMAC-SHA256 "second-factor-verified" token (`uid`, `exp`), 2h TTL matching Payload's session; `timingSafeEqual` compare.
  - `requestHelpers.ts` — parse/verify the step-up cookie from headers or Payload's cookie map; build set/clear `Set-Cookie` values.
  - `rateLimit.ts` — Upstash Redis sliding-window limiter (5/5min) when `UPSTASH_REDIS_REST_URL/TOKEN` are set; an in-memory fallback for local/CI (same "real service in prod, local stand-in for dev/CI" pattern as S3Mock; not safe multi-instance, warns if it ever activates in prod).
  - `qr.ts` — QR data-URL for the enrollment screen.
- `src/collections/Users.endpoints.ts` — custom endpoints under `/api/users/totp/*`: `setup` (mint secret + QR; re-enroll requires current step-up), `enable` (confirm a code, flip `totpEnabled`, set step-up cookie), `verify` (per-login second factor, sets step-up cookie, user+IP rate-limited), `disable` (requires step-up **and** password re-check), `status`.
- `src/access/requireTotpVerified.ts` — access wrapper: denies unless there's a `req.user`, `totpEnabled`, **and** a valid step-up cookie for that user id; then delegates to the wrapped access fn. **This is the security boundary.**

### Two real bugs surfaced during testing (both worth a fresh session knowing)

1. **Proxy verified the session JWT against the wrong key — the headline bug.** `src/proxy.ts` verified the `payload-token` with the **raw** `PAYLOAD_SECRET`. Payload does **not** sign with the raw value: on init it derives `crypto.createHash('sha256').update(config.secret).digest('hex').slice(0, 32)` (see `node_modules/payload/dist/index.js`, `BasePayload` init) and signs/verifies with `TextEncoder().encode(...)` of **that**. So every real token failed with `signature verification failed`; `verifiedPayloadUserId` returned `undefined`; the proxy fell through to `NextResponse.next()` and never redirected — the symptom was a password-only session landing on `/admin/collections/users` and seeing an empty "Nothing found" list (the access wrapper correctly denied the data; only the redirect UX was missing). The integration test masked it because it hand-signed its test tokens with the raw secret too — test and buggy proxy agreed with each other while both disagreed with reality. **Fix:** `payloadJwtKey()` in `proxy.ts` reproduces Payload's exact derivation and is **exported and reused by the int test**, so the two can't drift again. **Lesson:** the one piece of custom code re-deriving Payload's own behavior is exactly where reality diverged — from a confidently-worded but unverified comment ("does not hash or transform"). Verify such assumptions against the installed source, and never let a test re-implement the very thing it's meant to check.
   - **Diagnostic red herring worth not repeating:** this was first mis-attributed to Turbopack "not running" the proxy, because `.next/.../middleware-manifest.json` was empty. That file is empty *by design* for a **Node-runtime** proxy — those register in `functions-config-manifest.json`, not `middleware-manifest.json`. A brief switch of `dev` to `--webpack` was a wrong turn (it only added slow-compile timeouts) and was reverted; `dev`/`devsafe` stay on Turbopack. What actually pinned it was temporary `console.warn` instrumentation in the proxy: the dev-server log showed `jwtVerify FAILED: signature verification failed`, which is unambiguous. When a Node-runtime proxy "doesn't fire," instrument it and read the server console rather than reasoning about manifests.
2. **TOTP replay-window flake in the e2e suite (a test bug, not a code bug).** The "new session" test reused the account the enrollment test had *just* enrolled. When its login code fell in the same 30-second TOTP window whose time-step enrollment had already consumed, otplib's replay protection (correctly) rejected it — a ~50–70%-of-runs timeout depending on where the window boundary fell. The 2FA logic is right; the test was unrealistic (real "new session" logins happen long after enrollment). **Fix:** `seedEnrolledTestUser` seeds a dedicated, already-enrolled account with an untouched time-step; the new-session test uses that, which also removes a hidden test-1→test-2 ordering dependency.

### Verification
- `npm run test:int`: green (both new int files; `proxy.int.spec.ts` now signs with the derived key via the shared `payloadJwtKey`).
- `npm run test:e2e`: **now green in CI.** The `deploy-staging` job that shipped Phase 1 `needs: verify`, which runs the full e2e suite — so all 6 passed there (the replay-flake fix included), plus Filip's earlier manual redirect check. `npm run devsafe` (clean `.next` + restart) is required after any `proxy.ts` change — Next never hot-reloads the proxy file.

### Decisions worth a fresh session knowing

- **Push in dev/CI, migrate on deployed stages** — Payload's own recommended split, kept (not "push:false everywhere"). CI's `verify` job keeps pushing on boot against its ephemeral Postgres, so the test suite is untouched; only real stages are migrations-only. Having committed migrations present does **not** affect push mode (push ignores the migration files), so `test:int`/`test:e2e` stay green.
- **Migrate in CI, not `prodMigrations`** — the serverless-correct choice (see above), and what Payload's docs recommend for anything that isn't a long-running container.
- **Neon: migrations use the DIRECT (unpooled) URL** — DDL breaks through Neon's PgBouncer pooler (transaction pooling). Runtime stays pooled; only the CI migrate step uses the direct URL. This is the single most likely thing to get wrong, so it's called out in the workflow comment, README, `.env.example`, and TECHSPEC §10.5.
- **`TotpEncryptionKey` required, Upstash optional** — encodes the actual severity: no TOTP key = broken admin (hard-fail the deploy); no Upstash = degraded-but-working rate limiting (tolerated pre-launch).

### Sandbox constraints hit (and how they were worked around)

- **The `payload` CLI can't load the TS config in-sandbox** — it uses `tsx`→esbuild, and `@esbuild/linux-x64` isn't in the Windows-mounted `node_modules` (the same "native binaries are Windows-only" quirk from Phase 0). Worked around exactly as the content-model session did: load the config with Node 22's native `--experimental-strip-types` + a small `@/`-alias/extensionless resolve hook, and call `createMigration`/`migrate` on `payload.db` directly. One wrinkle: Payload's generated migration imports `MigrateUpArgs`/`MigrateDownArgs` as *values* (`import { MigrateUpArgs, MigrateDownArgs, sql }`), which `--strip-types` can't elide (only real `tsx`/esbuild does), so the sandbox apply-test patched that one import line in a scratch copy; **the committed file keeps Payload's original import** (correct for CI/Filip's toolchain).
- **`bwrap --unshare-pid --die-with-parent`** — every bash call is its own PID namespace, so **no process survives between calls** (background/`setsid`/`nohup` all die with the call). But the on-disk `pgdata` persists, so the pattern is: warm the cluster (`initdb`) once, then reuse the data dir in later calls (start is ~0.4s, no initdb). Also note `pkill -f postgres` **self-matches** the calling shell (its command line contains "postgres") and kills the call — use `pkill -x postgres` or, since nothing survives a call anyway, don't bother.
- **Stale mount reads** — after editing `package.json` via the Edit tool, the Linux side served a truncated pre-edit copy (2473 bytes, unterminated mid-string), which broke Node's module resolution for any in-sandbox eval. The Read tool (authoritative Windows view) confirmed the file was correct; the adapter-options check was rerun mount-independently (importing `@payloadcms/db-postgres` by absolute path). Same Windows↔Linux flakiness as always — trust Read/Edit/Write.

## How Phase 0 went (the Lambda spike)

Scaffolding (Next.js 16.2 + Payload 3.85 + Postgres/Drizzle + SST v4/OpenNext + GitHub Actions) went roughly as planned; getting Payload to actually serve on Lambda took five real, non-obvious fixes, none of which invalidated the architecture:
1. OpenNext copies externalized packages (`pg`, `pino`) into the Lambda bundle via symlinks that Windows can't reliably produce as Linux symlinks → **deploys go through CI (Ubuntu) only, never native Windows.**
2. `sharp` is excluded from the main server bundle by OpenNext and ships arch-specific binaries that don't cross-compile (x64 CI → arm64 Lambda) → omitted entirely (nothing in Media uses it; it's now also removed from `package.json`, keeping deps honest).
3. Media uploads need an explicit storage adapter (`@payloadcms/storage-s3`) — SST linking a bucket only wires IAM, it doesn't make Payload use it.
4. `admin/importMap.js` is generated, not static — regenerate (`npm run generate:importmap`) after any collection/field/plugin that contributes admin UI; silently stale otherwise.
5. IAM's `aws:RequestedRegion` doesn't scope global services (CloudFront/IAM/Route 53) → CloudFront needed its own unconditioned statement.

## Decisions made along the way (also reflected in TECHSPEC.md)

- **Repo structure**: single app at repo root, not a monorepo; `infra/aws/` holds only the one-time OIDC bootstrap that must exist before SST/CI can run.
- **GitHub Actions ↔ AWS**: OIDC federation (short-lived assumed role), scoped to the exact repo **and** the `staging` GitHub Environment.
- **IAM deploy policy**: broad-but-region-scoped Allow + explicit Deny on high-risk actions; **tighten with IAM Access Analyzer before reusing for a `production` role** (still a tracked follow-up).

## Environment quirks worth knowing (specific to this Cowork/Claude sandbox, not the app)

- The Linux sandbox's view of the Windows-mounted repo has intermittent caching problems: `git status`/`git diff`/`cat` sometimes show stale or truncated content. **Trust the Windows-native `Read`/`Edit`/`Write` tools over bash; cross-verify with `git show HEAD:<path>`.** When bash's copy of a file looks stale, rewrite it via a heredoc (`cat > path <<'EOF' ... EOF`) from content confirmed by `Read`.
- **Do not run `git add`/`commit`/`push` from the sandbox** — a stale `.git/index.lock` once could not be removed (`rm` returns `Operation not permitted` on the Windows mount). Filip commits via his own tooling (GitHub Desktop). The same permission quirk means the sandbox **cannot delete files** on the mount — e.g. `smoke-test-tmp.mjs` (a harmless leftover, untracked) had to be left for Filip to delete manually.
- `npm install`/`sst install`/large builds can exceed a single sandbox command's time limit; retrying converges.
- **Turbopack cannot run in this sandbox** — only WebAssembly SWC bindings are available, and Turbopack requires native bindings (`Turbopack is not supported on this platform`). For any in-sandbox `next build`/`next dev` reproduction, use `--webpack`. Filip's real machine (Windows) uses Turbopack, which is the Next 16 default for both `dev` and `build`; keep that distinction in mind when reproducing bundler-adjacent behavior (it's why the Turbopack red herring above was hard to rule out from the sandbox alone).
