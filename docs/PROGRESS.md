### The standing rules this project learned the hard way

- **Verify against the installed source and the live system, never against docs, `npm audit`'s "fix available", or a previous session's conclusion.** The highest-value fixes here (security headers, the `/api/quote` limiter, the `users.unlock` gate, the silent no-op migrate step, the non-deterministic axe gate, the unsent password-reset email) were all found by re-reading code or running the product after a session had concluded "everything remaining is externally gated".
- **A passing CI step must prove its post-condition** (the migrate step "passed" for six weeks while applying nothing).
- **Prove a regression test fails without its fix**, both directions, before trusting it.
- **A comment in `.env` is not a guard; a process that refuses to start is** (`src/lib/dbGuard.ts`).
- **Every Payload access operation must be set explicitly — `read`, `create`, `update`, `delete`, `unlock`, `readVersions` — and every public read on a draft-enabled entity needs a `_status` constraint.** Payload's fallback for an unset access function is `Boolean(req.user)` (any password-only session), and `?draft=true` restricts nothing on its own; the `unlock` gap (2026-09-10), the versions gap and the `LegalInfo` draft leak (2026-09-18) were all the same lesson.
- **Every Dependabot/CodeQL finding gets a decision, in the repo:** a version bump in the lockfile, an `overrides` entry for a transitive package the direct dependency will not move (`qs`, `@esbuild-kit/core-utils`→`esbuild`, `@lhci/cli`→`uuid`), or — only when no patched release exists AND the code path is provably unreachable — a dismissal whose reason is written down here.
- **Any client-side navigation across an authorisation boundary must be a hard navigation** (`window.location.assign`) — the App Router's client cache replays prefetched redirects.
- Deploy through CI (Ubuntu), never `sst deploy` from Windows; `npm ci` before any local build; `npm run devsafe` after a `proxy.ts` change.

### Pre-launch integrity hardening + dependency/code-scanning sweep — 2026-09-18

**Found by reading and probing, not by the roadmap** — a line-by-line pass over every source, test, infra and doc file, checked against the installed `payload@3.89` / `@payloadcms/storage-s3` / SST sources and the live stages.

1. **`LegalInfo` draft leak.** `read: () => true` was justified by "a plain read returns only the published main row" — true, but `?draft=true` makes Payload's `findOne` swap in the newest version from the versions table and, with a boolean-true access result, filter that query by NOTHING (`versions/drafts/replaceWithDraftIfAvailable.js`). Reproduced with the real `REST_GET` handler: an anonymous `GET /api/globals/legal-info?draft=true` returned the unpublished draft — exactly the placeholder registration details §6.9 says must never surface. Payload's docs are explicit that `draft` restricts nothing and `_status`-based read access must. Fix: `readPublishedOrVerified` (the same rule the collections already had). With a WHERE access result the draft lookup is constrained to `version._status = published`, so the public gets the published row or `{}`; the public pages behave exactly as before.
2. **`readVersions` gap.** No collection or global set it, and Payload's fallback for an unset access function is `Boolean(req.user)` (`auth/executeAccess.js`) — a password-only session (no TOTP) could list every draft through `GET /api/{services,projects}/versions` and `/api/globals/legal-info/versions`. Anonymous was 403 (checked on production). Same class as `users.unlock`. Fix: `readVersions: requireTotpVerified(() => true)` on Services, Projects, LegalInfo.
3. **Media.** (a) No file-size limit anywhere, while every byte is served through the Web Lambda, which OpenNext builds **buffered** (`"streaming": false` in `.open-next/open-next.output.json`): Lambda's buffered response cap is 6 MB *after* base64, so a phone photo over ~4.5 MB uploads "successfully" (direct-to-S3) and then 502s on the public site. (b) `getFile` sets no `Cache-Control`, so CloudFront re-fetched every image on every request (Lambda + S3 HEAD + GET) and browsers revalidated on every navigation. (c) `clientUploads` presigned PUT URLs were granted on the plugin's default `!!req.user` — a password-only session could write bytes into the media bucket. Fixes, one number (`MEDIA_MAX_FILE_BYTES` = 4 MB): `upload.limits.fileSize` + `abortOnLimit` (busboy 413 on multipart; the storage-s3 plugin re-checks the same option when it mints presigned URLs and signs `content-length` so S3 enforces it — verified in `dist/generateSignedURL.js`); a Media `beforeValidate` hook on `filesize` + `mimeType` for every path incl. the Local API; `modifyResponseHeaders` → `public, max-age=3600, s-maxage=86400`; `afterChange`/`afterDelete` revalidate hooks so a replaced file purges the edge; `clientUploads: { access: isFullyVerified }`; admin copy says "up to 4 MB".

### Admin password reset, Payload CSRF allowlist, header hardening — 2026-09-16/17, commit `bd38da4`

**Found by reading, not by the roadmap.** FUNCTIONALITY §5.1 / TECHSPEC §6.6 said the admin "receives a reset link by email … via SES". Verified against the installed `payload@3.89.0` source, none of it existed:

1. No `email` adapter → Payload's console adapter logs *"Email attempted without being configured"* and returns success. "Forgot your password?" showed *Email Sent*; nothing was sent. One admin + mandatory 2FA = an unrecoverable password without DB access.
2. No `serverURL` → `utilities/getRequestOrigin.js` refuses the Host header (correct — host-header injection) and returns `''`, so even with an adapter the reset link would have been the relative `/admin/reset/<token>`.
3. No `serverURL`/`csrf` → `csrf = []`, and `auth/extractJWT.js` accepts the `payload-token` cookie from **any `Origin`** when the list is empty. Payload's CSRF allowlist was disabled; SameSite=Lax was the only defence. (Payload's docs imply the opposite; the source is what runs.)

**Built (no new dependency, no schema change):**

Not configured outside production → prints the message (incl. the reset link) to the server console so the flow is completable locally; not configured in production → one `OPS_ALERT` (`email.payload.notConfigured`), body never logged. Chosen over `@payloadcms/email-nodemailer` (SES SMTP = a new long-lived secret) and Resend (a new sub-processor).
- `src/lib/email/resetPasswordEmail.ts` — branded mail per the OWASP Forgot Password cheat sheet (link only, expiry stated, "ignore if not you", everything escaped).
- `src/lib/serverUrl.ts` — `resolveServerUrl()`: `NEXT_PUBLIC_SITE_URL` (the `SiteUrl` secret) → else `https://bulbau.lu` **only on the SST production stage** → else `http://localhost:3000` outside production mode → else `''`. A staging stage without `SiteUrl` keeps the old permissive behaviour and logs a loud warning instead of locking its admin out; a CI `next build`/`next start` is never mistaken for production (`readSstStage()` has no `NODE_ENV` fallback).
