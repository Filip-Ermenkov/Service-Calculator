## 1. Guiding principles

1. **Best tool for the job, not the biggest brand.** AWS-native is a fine default, not a rule. A component is chosen because it's the best fit for this workload's actual shape (single admin, low-to-moderate public traffic, bursty usage), not because it's from the same vendor as everything else.
2. **Cheap now, portable later.** Every stateful piece of this system (database, media) uses a standard, portable technology (Postgres wire protocol, S3-compatible object storage) so that swapping the compute layer later is an infrastructure change, never a data migration or a rewrite.
3. **Security is not a budget line.** Encryption, secrets hygiene, 2FA, input validation, and dependency hygiene cost effectively nothing regardless of hosting tier and are non-negotiable from day one. What *does* scale with budget is redundancy/uptime (multi-AZ, standby capacity) — that's an explicit, revisitable business decision, not a security gap.
4. **Ship in slices.** Each phase in Section 12 is built, manually and automatically tested, and confirmed working end-to-end before the next phase starts.
5. **No proprietary lock-in on data.** Postgres over SQLite/DynamoDB for the primary store, specifically so a future migration between hosting providers is a `pg_dump`/`pg_restore`, not a data model port.

## 2. Architecture overview

The application is a single Next.js (App Router, TypeScript) codebase with **Payload CMS 3.x embedded directly in it** (Payload 3 runs inside a Next.js app rather than beside it — same repo, same deploy artifact, same server). Payload provides: the admin panel framework, authentication, localization (EN/FR/DE), media uploads, draft/publish workflow, and auto-generated REST/GraphQL/Local APIs. Everything Payload doesn't provide out of the box (formula builder, TOTP 2FA, PDF generation, translation pipeline) is built as custom code inside this same app.

### 2.1 Two deployment topologies, one codebase

This project deliberately runs through **two infrastructure phases** without ever changing the application code:

```
Phase A — Serverless (now → until sustained traffic justifies otherwise)
──────────────────────────────────────────────────────────────────────
 Visitor / Admin
      │
      ▼
 CloudFront  ──── S3 (static assets, uploaded media)
      │
      ▼
 Lambda (Next.js + Payload, via OpenNext)  ──── Lambda (PDF generation, isolated)
      │
      ▼
 Neon (serverless Postgres, scale-to-zero)

Phase B — Containers (triggered by sustained load, not "growth" per se)
──────────────────────────────────────────────────────────────────────
 Visitor / Admin
      │
      ▼
 CloudFront  ──── S3 (unchanged)
      │
      ▼
 ALB → ECS Fargate (same Docker image, same app code)
      │
      ▼
 RDS / Aurora Postgres (data restored from Neon via pg_dump/pg_restore)
```

The only things that change between Phase A and Phase B: the compute target (Lambda function → Fargate service/container) and the Postgres host (Neon → RDS/Aurora). The domain, CloudFront distribution, S3 bucket, application code, database schema, and all content are untouched. See Section 11 for the exact migration procedure and trigger criteria.

## 6. Feature implementation plan

### 6.1 Global behaviour (language, responsive, header/footer)
`next-intl` middleware resolves `/en`, `/fr`, `/de` prefixes; initial visit is redirected based on `Accept-Language`, then the choice is persisted in the URL (not just a cookie) for indexability. Header/footer are shared layout components pulling contact details from the `CompanyInfo` singleton, so a single edit propagates everywhere per the requirement in `FUNCTIONALITY.md` §5.6.

> **✅ Built in Phase 2 part 1 (2026-07-17).** next-intl v4 with `localePrefix: 'always'`; the middleware lives in `src/proxy.ts`, **composed** with the pre-existing TOTP admin gate by path (`/admin/*` → gate, else → i18n). The localized site is a top-level `src/app/[locale]/` root layout. **Divergence from the plan, corrected here:** responsive layout is **not** Tailwind — the approved prototype was authored in hand-written CSS, so its design system was ported verbatim into `src/app/[locale]/globals.css` (lower-risk than re-expressing it as Tailwind utilities, and pixel-faithful to the sign-off). Fonts self-hosted via `next/font`. UI chrome is fully trilingual now (`src/i18n/messages/`); CMS content falls back to EN until Phase 5.

### 6.2 Public pages (Home, Projects, About, Careers)
Rendered with Next.js static generation + on-demand revalidation (ISR), invalidated via a Payload `afterChange` hook that calls Next.js's on-demand revalidation API whenever content is published. This means most public traffic is served from CloudFront's cache and never invokes the Lambda function at all — which is both fast and keeps Lambda invocation counts (and cost) low. Projects page search/filter runs client-side against a small pre-fetched dataset (this site's project count doesn't justify a search backend).

> **As built.** ISR `revalidate = 300` per page plus on-demand revalidation from `afterChange`/`afterDelete` hooks (`src/lib/revalidate.ts`), which revalidates **each content page pattern explicitly by `'page'` type** (a `layout` revalidation does not cascade into dynamic routes on OpenNext) and then **invalidates CloudFront on demand** (`src/lib/cdn/invalidate.ts`) — OpenNext's automatic CDN invalidation is a no-op, so without this a publish stayed stale at the edge until `s-maxage`. The distribution id reaches the server function through an SSM parameter created *after* the Nextjs component (SST #5990 cycle). Data reads use the Local API with `overrideAccess: false` (`src/lib/content.ts`), never throw, and emit `OPS_ALERT` on failure (§8.1). Service URLs are slugs; the Projects search/filter is a client component over a server-pre-fetched list; the public projects order follows the admin's drag order.

### 6.3 Service page & real-time calculator
Each service's `calculatorFields` + `formula` are fetched once per page load. The formula is evaluated client-side with the same evaluator used server-side, so the live price updates on every change with no round trip, matching `FUNCTIONALITY.md` §3.3. The zero/negative-result edge case (§7) is handled inside the evaluator wrapper: any non-positive result renders "Contact us for a price" instead of a number, on both the web page and the PDF.

> **✅ Built in Phase 3 part 1 (2026-07-19).** The shared evaluator is `src/lib/pricing/` — a pure, framework-free module (`computePrice`, `evaluateJsonLogic`, `formatCurrency`, input coercion, line-item contributions) with **zero dependencies**, so it runs identically on the client (`ServiceCalculator.tsx`), on the server, and (Phase 4) in the PDF Lambda — the on-screen price can't drift from the quote. The stored `formula` is **standard JSONLogic**; the interpreter supports the arithmetic subset a pricing engine needs (`var`, `+ − × ÷`, `min`/`max`, nesting for order-of-operations) and treats any unsupported/malformed rule as "can't price it → Contact us". `json-logic-js` was **not** adopted (unmaintained); the format is library-agnostic so a maintained engine (`json-logic-engine`) can drop in later with no data migration. **Default path** (no formula) = Σ signed `unitPrice × value`; a custom formula, when present, is authoritative over raw field values (fixed costs / %-adjustments / groupings). The public total is **gated on required fields** (an explicit 0 counts as filled), with hard/blocking validation deferred to PDF generation (Phase 4). EUR is `Intl.NumberFormat`-formatted per locale. Full detail + the engine-decision rationale in `docs/PROGRESS.md` (Phase 3 part 1).

### 6.4 Calculator Field Builder & Formula Builder (admin) — Phase 3 **part 2** (built 2026-07-20)
Built as a custom Payload field component (React, mounted in the `Services` collection edit view):
- Field list editor: label, type (number/dropdown/toggle), options, multiplier, sign (+/−), required flag, drag-to-reorder.
- Formula builder: a structured (not free-text) UI for grouping fields, fixed costs, and percentage adjustments, serialized to a JSONLogic AST — never a string of executable code.
- Live preview panel evaluates the in-progress formula against sample values using the exact same evaluator the public page uses, so what the admin sees in preview is guaranteed to match production behaviour.

> **As built.** The **Calculator Field Builder** is the native Payload `calculatorFields` array (label, `fieldKey`, type, options, unit price, +/− sign, required, `unit`, `defaultOn`, drag-reorder). The 2026-07-20 structured terms/groups/%-builder was replaced on 2026-09-14 by the formula bar below; the stored value never changed.

> **🔁 Rebuilt 2026-09-14 — the Formula Builder is now a FORMULA BAR.** The structured terms/fixed-costs/groups/%-adjustments builder above could not express "any formula": field × field needed a group workaround, and tiers, minimum charges, caps and rounding were impossible. It was replaced by the pattern every no-code tool (Airtable, Notion, Coda, spreadsheets) converged on, and which the prototype's `service-editor.html` had already sketched: a **free-form expression** with syntax highlighting, bracket matching, autocomplete, click-to-insert chips, plain-language errors and inline reference. The admin writes `(area × rate + 200) × (1 + 17%)`, `if(area > 100, area × 10, area × 12)`, `max(area × 12, 500)`, `ceil(area / 1.7) × 250`. **Language** (`src/lib/pricing/formulaExpression.ts`, pure, unit-tested): precedence `or` < `and` < `not` < comparisons `< > ≤ ≥ = ≠` < `+ −` < `× ÷` < unary `−` < postfix `%` (`17%` ≡ 0.17); functions `if` (with else-if pairs), `min`, `max`, `round(x[, decimals])`, `ceil`, `floor`, `abs`, `mod`; `* / - != <= >=` and `;` accepted alongside the typographic forms; field references are the calculator fields' **`fieldKey`s** (bare when identifier-shaped, `{braced}` otherwise). Every error is plain-language with a character range — *Unknown field "aera". Did you mean "area"?*, *Use a dot for decimals: write "1.5", not "1,5"*, *Missing a closing bracket )*. **Storage is unchanged**: the text compiles to the same JSONLogic on every edit and is printed back on load (presentation normalises — `*`→`×`, `17%`→`0.17`, redundant brackets dropped — arithmetic never changes), so the public calculator, the evaluator (extended, see §3) and the PDF are untouched and there was **no migration**; formulas saved by the previous builder re-open as text. **Invalid formulas cannot be published:** while the text does not parse the field holds `{ "__draft": "<text>" }` (nothing typed is lost), and `Services.formula`'s new server-side `validate` — also registered client-side via `useField({ validate })` — refuses the marker, unsupported operators, wrong arity and any `var` naming a field that no longer exists; `fieldKey` is validated unique/space-free. The UI (`src/components/admin/FormulaBuilder.tsx`) is a transparent `<textarea>` over a `<pre>` highlight layer (identical metrics; colour only), an autocomplete listbox (`aria-autocomplete="list"`), a "Reads as" echo with field labels, a *Start from the default sum* prefill, the chips, a collapsible recipe reference, the raw-JSON escape hatch, and the unchanged Test / Preview tab (same `computePrice()`, same required-field gating). Tests: `tests/int/formulaExpression.int.spec.ts` (40) + an e2e proving Publish is refused on a broken formula. Full record: `docs/PROGRESS.md` → "Formula bar, unified admin lists, fail-closed migrations, TOTP fixes".

### 6.6 Admin panel & authentication
Payload's admin UI is used as-is for Projects, Careers, and CompanyInfo (no custom UI needed there — this is exactly what "off-the-shelf CMS admin" is good at).

Where `EMAIL_SENDER` is unset the adapter prints the message to the console outside production and emits an `OPS_ALERT` in production. A reset never bypasses 2FA: the auto-login Payload performs afterwards is a password-only session, which the gate sends to `/admin/totp-verify`.

### 6.7 Translation management & lifecycle
On save of any localized field, a Payload hook computes a hash of the English source and enqueues a Jobs Queue task (processed by a scheduled Lambda) that calls the DeepL API for FR and DE if no manual override exists, or flags `needsReview: true` if an override exists and the source hash changed. The Translation Management screen (custom Payload admin view) lists every translatable string, its auto-translation, any override, and review status, matching `FUNCTIONALITY.md` §5.7 exactly.

> **As built.** (1) **AWS Translate, not DeepL** — DeepL's recurring free tier is gone; Translate authenticates via the Lambda execution role (no secret, no new sub-processor) with a FORMAL fr/de register, isolated behind `src/lib/translation/provider.ts`. (2) A **synchronous `afterChange` hook**, not the Jobs Queue (`autoRun` is not for serverless; Next's `after()` is unsupported on OpenNext). Because the hook runs inside the save transaction it is paced under the 20 req/s quota, bounded by a 12 s deadline under a 30 s Lambda timeout, never throws, processes locales sequentially and guards recursion by mutating `req.context`; it revalidates the site exactly once itself. (3) **No shadow collection** — a field is (re)translated iff its EN source changed or the target still equals the EN fallback, so overrides survive. The **Translation Management screen** (`/admin/translations`, `src/lib/translation/inventory.ts`, `POST /api/admin/translations`) reviews every string at `locale: 'all'`, edits plain text inline (override / re-translate) writing the target with `fallbackLocale: false` so untranslated siblings are never persisted as EN, and deep-links rich text to the native localized editor. Deferred: persisted auto-vs-override + "needs review" flagging (needs the shadow collection + a migration).

### 6.10 Analytics — deliberately out of scope
**Decision (2026-07-18): the site ships with no web analytics.** Analytics serves the *site owner* (traffic volume, referral sources, which pages get attention) — it is not a technical requirement, does nothing for SEO (a private measurement layer Google never sees; if anything one fewer third-party script is marginally faster), and its absence removes a recurring subscription (Plausible Cloud) or an always-on self-hosted service for no launch-critical benefit. An earlier plan to add Plausible was evaluated and reversed after weighing it against the project's actual priorities (SEO/web visibility) and its "periodic maintenance only" goal.

The privacy posture is *unchanged and lean*: with no analytics, the only cookie anywhere is the strictly-functional language preference, so there is still **no cookie-consent banner** (correct, not a compromise — nothing non-functional to consent to).

**If a site owner later wants visitor stats**, add a cookieless tool as a small dedicated slice: self-hosted **Umami** colocated in the SST stack (no subscription; tears down with `sst remove`), or a **client-owned Plausible account** (the billing risk sits with the client, not the operator). The integration point is a single script tag behind one env flag — trivial to add on demand.

## 7. Security baseline (applies regardless of hosting tier)

- Passwords hashed with a modern algorithm (Payload default, verified to be argon2id-equivalent strength); TOTP secrets encrypted at rest.
- **Every access operation on `Users` requires the completed second factor — including `unlock`.** Payload gives an auth-enabled collection five access operations; `unlock` (which clears the `maxLoginAttempts`/`lockTime` lockout) had been left on the framework default `Boolean(user)`, so a stolen password could reset the brute-force defence. `Users.ts` sets `unlock: requireTotpVerified(() => true)`; `tests/int/rest.int.spec.ts` pins it. GHSA-jg8r-5jh2-v2xj lists no patched version — a Payload upgrade does not cover this.
- **Any client-side navigation that crosses an authorisation boundary must be a HARD navigation** (`window.location.assign`), not `router.push()`: the App Router's client Router Cache can replay a route prefetched under the previous authorisation (a correct 2FA code looped back to the code screen on Next 16.3.4). `router.refresh()` does not help; Next exposes no full-cache invalidation.
- All traffic TLS-only (CloudFront enforces HTTPS; HTTP redirects).
- **HTTP security response headers** — one source of truth, `src/lib/security/headers.ts`, served on every route by `next.config.ts` `headers()` **and applied by `src/proxy.ts` to the redirects it terminates itself** (the `/` → `/<locale>` 307 and the admin gate's redirect shipped without any headers until 2026-09-16, because `headers()` never sees a proxy-terminated response). The set: HSTS 2 years + `includeSubDomains` (`preload` deferred to the launch step), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: SAMEORIGIN`, `X-XSS-Protection: 0`, `X-Permitted-Cross-Domain-Policies: none`, `Cross-Origin-Opener-Policy: same-origin`, a restrictive `Permissions-Policy`, and a **nonce-free CSP** (`base-uri 'self'; object-src 'none'; frame-ancestors 'self'; form-action 'self'` — deliberately no `default-src`/`script-src`/`style-src`, which would need per-request nonces and can silently break the Payload admin; that ratchet is a Phase 7 design decision). `X-Powered-By` is removed (`poweredByHeader: false`; `withPayload` honours it). Covered by `securityHeaders.int` + `securityHeaders.e2e` + `accountRecovery.e2e`.
- **Rate limits on every unauthenticated endpoint that does expensive or outbound work**, all through the shared `src/lib/rateLimit.ts` (Upstash sliding window on deployed stages once configured; in-memory fallback locally/CI) and keyed by `getClientIp` (`CloudFront-Viewer-Address` → **last** `X-Forwarded-For` hop → `x-real-ip` → a constant fail-safe bucket; CloudFront strips viewer-supplied `CloudFront-Viewer-Address`/`X-Real-IP` and appends the true IP last): `/api/quote` 10 / min / IP + 16 KB and 200-field caps (a Neon read + the 1600 MB Chromium Lambda per call), `/api/contact` 5 / min / IP + 32 KB cap, TOTP verify/enrol 5 / 5 min per user and per IP, `/api/users/forgot-password` 5 / 15 min per IP and per address (an SES send per call). Limited callers get `429` + `Retry-After` before any work. Follow-up: forward `CloudFront-Viewer-Address` on the production distribution for full spoof-resistance.
- **Payload's cookie-CSRF allowlist is active (2026-09-16).** `payload.config.ts` sets `serverURL` (resolved per stage by `src/lib/serverUrl.ts`; Payload's sanitizer copies it onto `csrf`), so the `payload-token` cookie is honoured only for requests whose `Origin` is this stage's origin — or, for same-origin GETs that carry no `Origin`, whose `Sec-Fetch-Site` is `same-origin`/`none`. Verified in the installed `payload@3.89` source: with an **empty** `csrf` list (the previous state) the cookie is accepted from **any** origin. The same `serverURL` is the only origin ever used in emailed links (host-header injection is impossible by construction). `SiteUrl` must be set on every deployed stage; a staging stage without it keeps the permissive behaviour and logs a warning rather than locking its admin out. The custom `/api/admin/*` routes and the TOTP endpoints re-check `payload.auth()` + the step-up cookie themselves.
- Secrets never in source or environment files committed to git — SSM Parameter Store / Secrets Manager only, referenced by ARN in SST config.
- Dependency scanning (`npm audit` / GitHub Dependabot) in CI. **Standing rule (earned 2026-09-10): verify an advisory against its own advisory page AND the installed source, never against `npm audit`'s "fix available"** — npm infers a fix from the affected-range boundary, so a bump can silence a finding while changing nothing (see the `unlock` case above). `package.json` `overrides` are used to pull patched transitive versions inside their declared ranges (`sharp`, `fast-uri`, `undici`, `baseline-browser-mapping`, …). **The gate is scoped to the *production* dependency tree** — `npm audit --omit=dev --audit-level=high` fails the build (this is the code that ships to the Lambda), and a full-tree audit runs **informational, non-blocking** for visibility (updated 2026-07-27, see `docs/PROGRESS.md` → "AWS account migration + dependency/CI hardening"). Rationale: a dev-only tooling advisory with no runtime exposure and no available fix in the pinned toolchain (e.g. a `brace-expansion` DoS patched only in an ESM-only line that eslint 9's CJS `minimatch@3` can't consume without moving to eslint 10, which breaks `eslint-plugin-react`) must not block a *deploy* — but every runtime advisory still gates (verified: `next`/`sharp`/`fast-uri` are production deps and still fail the gate).
- Input validation on every route handler (hand-written bounds/type checks — no Zod was added; the bodies are tiny) on top of Payload's field validation, including the server-side `validate` on `Services.formula`/`fieldKey`. `Media` accepts only jpeg/png/webp (an SVG served same-origin is stored XSS). JSON-LD is serialised with `<` escaped.
- Login lockout (Payload `maxLoginAttempts`/`lockTime`) on the first factor; the limiters above on everything else.
- Least-privilege IAM at runtime: the Web function's role carries only `translate:TranslateText`, `ssm:GetParameter` on its one parameter, `cloudfront:CreateInvalidation`, `ses:SendEmail` on this account's identities, S3 on the media bucket and invoke on the Pdf function; the Pdf function has no Payload, no database and no SES. The CI deploy role is broad-but-region-scoped with explicit Denies (an IAM Access Analyzer pass is a Phase 7 item — `infra/aws/README.md`).
- CloudFront + Shield Standard (free) from day one; AWS WAF and GuardDuty are deferred cost-wise (Section 9) but are a config addition, not an architecture change, whenever traffic/risk profile justifies them.

## 7A. Compliance & data residency (GDPR)

This is a Luxembourg business serving EU visitors, so GDPR applies regardless of hosting location, and data residency choices should reflect that:

- **Region**: EU AWS region — `eu-central-1` (Section 3), not US.
- **Minimal data footprint by design**: the contact form is relayed straight to the company's inbox and never persisted in the database; PDF quotes are generated on demand and never stored (both already specified in `FUNCTIONALITY.md` §3.3/§4). This meaningfully shrinks the GDPR surface compared to a site that stores visitor submissions.
- **Sub-processors**: AWS (incl. **AWS Translate**, which as of 2026-08-02 replaced DeepL — so translation is now in-account AWS, one fewer external sub-processor), Neon, and Cloudflare (Turnstile) all process data on the company's behalf and each need a Data Processing Agreement in place — all publish standard DPAs, but this needs to actually be reviewed and accepted during Phase 0 setup, not assumed. (DeepL is no longer used; drop it from any DPA checklist.)
- **Cookie/consent — resolved**: the site runs no web analytics (§6.10), so the only cookie anywhere is the strictly-functional language preference. That requires no consent under GDPR/ePrivacy, so the site ships with **no cookie-consent banner**. (If analytics is ever added, it must be a cookieless tool so this stays true.)
- **DPO — resolved**: this business's data processing (contact-form inquiries only, no large-scale or special-category data) doesn't meet GDPR Article 37's threshold for a mandatory Data Protection Officer. The admin/business owner is listed as the data controller in the Privacy Policy instead.
- **Retention — resolved**: no fixed retention period is specified; the Privacy Policy states messages are kept only as long as needed to respond, then deleted per normal business practice.
- **Legal Notice / Privacy Policy — specified, not yet publishable**: both pages are now fully specified in `FUNCTIONALITY.md` §2.5 and implemented per Section 6.9. They cannot go live with placeholder legal details — the company's registered legal form, RCS Luxembourg number, VAT number, and registered address are still pending from the client and are a hard gate on Phase 6 sign-off, enforced technically (Section 6.9), not just procedurally.

## 7B. Accessibility (WCAG 2.1 AA)

Not previously specified anywhere in this document — added on review, not because a client or legal mandate demanded it, but because it's current best practice for any public-facing site and is far cheaper to build in than to retrofit:

- Target WCAG 2.1 AA: semantic HTML landmarks, full keyboard navigation (including the calculator and the admin panel's custom formula-builder component — the easiest place for a custom UI to silently fail this), visible focus states, sufficient color contrast carried over from the already-approved prototype's design, and required alt text on all media (Section 5).
- The EU's Accessibility Act (in force since June 2025) most clearly covers e-commerce; whether a quote-generation (not transactional) site like this falls squarely within its scope is genuinely ambiguous and not worth over-claiming either way — but WCAG 2.1 AA is the right bar regardless of whether it's strictly mandated here.

## 8. Non-functional expectations (current phase)

Given this is a single-administrator marketing/lead-generation site with no payment processing and modest traffic:

- No formal uptime SLA. Occasional brief unavailability from a cold Lambda/Neon resume after an idle period is an accepted trade-off for near-zero cost (Section 9).
- No multi-AZ/HA requirement yet. Revisit if/when the business depends on continuous availability or compliance requires it.
- Backups: Neon's point-in-time recovery in Phase A; RDS automated backups + snapshots in Phase B.
- Observability: CloudWatch logs + alarms (§8.1). The SST-side alarms are created by every deploy; the Terraform-side uptime/CloudFront alarms are enabled in the live `terraform.tfvars` — proving end-to-end delivery (a synthetic `OPS_ALERT`, `set-alarm-state`, the us-east-1 SNS confirmation) is on the Phase 7 list. Expand to structured tracing if/when traffic grows.

### 8.1 Failure visibility (built 2026-09-10)

The two failure modes this app can produce that ordinary Lambda alarms **cannot see**, and what covers each:

| Failure | Why the obvious alarm misses it | Covered by |
|---|---|---|
| Neon unreachable | `src/lib/content.ts` never throws — it returns `[]`, so the whole public site renders as **blank pages with HTTP 200**, and ISR/CloudFront then cache the blank version | `OPS_ALERT` log-metric alarm |
| A rendering fault | OpenNext/Next returns a 500 **response** without the handler throwing, so `AWS/Lambda Errors` stays at zero | `OPS_ALERT` alarm + the CloudFront `5xxErrorRate` alarm |
| A failed contact-form relay | Returns `{ ok: false }` by design (§7 download/retry fallback) — a lost customer enquiry, invisible | `OPS_ALERT` (severity `error`) |
| Site unreachable (DNS, cert, CloudFront, cold origin) | No Lambda is invoked at all, so no Lambda metric exists | Route 53 health check on `/api/health` |
| Web function throttled | Was simply not alarmed on (only the Pdf function was) | Web `Throttles` alarm |

**`OPS_ALERT` — the app→infrastructure contract.** `src/lib/observability/opsLog.ts` writes ONE single-line marker per event; a CloudWatch Logs **metric filter** matching the literal `OPS_ALERT` turns it into a metric an alarm watches. Invariants the filter depends on (exactly one line, marker first, never throws, no stack traces or user data) are pinned by `tests/int/observability.int.spec.ts`. Self-healing degradations use a **separate `OPS_WARN` marker** the filter does not match, so a missed CDN purge is greppable without paging anyone — the distinction lives in the marker rather than a `severity` JSON field because CloudWatch's unstructured filter syntax makes "literal AND nested field" an escaping hazard.

**`GET /api/health` — liveness, deliberately NOT a deep check.** It confirms the request reached this deployment and required runtime config is present, and returns 503 when it is not. It **does not touch the database**, and that is an architectural constraint rather than laziness: Neon scale-to-zero is load-bearing for the cost model in §9, and a probe every 30 seconds would keep the database awake 24/7 — monitoring that breaks the thing it monitors. The database-failure case is covered by `OPS_ALERT` instead. **Stated trade-off:** that fires when a real request hits the fault rather than proactively, which for a cached, low-traffic marketing site is the right bar. The response body is deliberately dull (status, stage, timestamp) since the endpoint must be unauthenticated for Route 53's checkers.

**Cost.** The alarms and the metric filter are effectively free (first 10 alarms free, then €0.10 each; one custom metric). The Route 53 health check adds **~$1.00–1.50/month** (base + the HTTPS optional feature). It is pinned to **3 checker regions** at the standard 30s interval: the default region set (~15 checkers) would be ~1.3M Lambda invocations/month and would exceed the 1M free tier on its own.

## 10. Infrastructure & deployment details

### 10.1 Environments
`local` (Docker Compose Postgres, or a **personal** Neon dev branch — never a stage's branch: since 2026-09-16 push mode refuses any non-local `DATABASE_URL`, see §10.5 "Local-push guard"), `staging` (separate Neon branch + separate Lambda/S3/CloudFront stack via SST), `production`.

**AWS account structure (as of 2026-07-27).** The app runs in its **own dedicated AWS account, `service-calculator-production` (`847321857537`)**, under `OU-Production` in the OrgFormation-managed organization (baseline + region-control SCPs applied there). It was **migrated out of the shared `acc-test` account (`176971015975`)** — which also hosts an unrelated online shop — because Lambda's concurrent-executions quota is **per-account** (and defaulted to 10, risking cross-app throttling) and for blast-radius isolation, both standard AWS multi-account guidance. Both the `staging` and the **`production`** SST stages now deploy into this account — **the `production` stage went live 2026-07-31** on the custom domain `https://bulbau.lu`, using the project's default Neon branch (baselined via `migrate:fresh`) and reusing the same OIDC deploy role (its trust policy widened to allow both the `staging` and `production` GitHub Environments). Full migration runbook + the deploy-role permission fixes in `docs/PROGRESS.md` → "AWS account migration"; the production stand-up (domain block, `deploy-production` job, ACM/Route 53 IAM additions) in `docs/PROGRESS.md` → "Production stage stand-up".

### 10.2 CI/CD (GitHub Actions)
1. Lint + typecheck + unit/integration tests on every PR, then a **schema-drift guard** (see §10.5 — `migrate:create --skip-empty`, failing the job if the committed migrations don't capture the current Payload schema) and a **generated-artifact drift guard** (see §10.5 — regenerates `payload-types.ts` + `admin/importMap.js` and fails on any diff, so stale types or a stale import map can't reach a deploy), then (before the production build) a content-seed step (`npm run seed:ci`, `ALLOW_CONTENT_SEED`-guarded) that publishes one sample service into the job's ephemeral Postgres so the `/services/[slug]` audits — axe (§7B) and Lighthouse (§6.11) — and the calculator/quote e2e tests run against a real service instead of skipping on an empty DB. The row persists across the build → Lighthouse → e2e steps in that one job.
2. On merge to `main`: apply DB migrations to staging (`payload migrate`, direct/unpooled Neon URL — Section 10.5) → deploy to staging via `sst deploy --stage staging` → run E2E suite, Lighthouse CI (Section 6.11), and axe-core accessibility checks (Section 7B) against staging → **manual approval gate on the `production` GitHub Environment** → migrate production (against `PRODUCTION_DATABASE_URL_UNPOOLED`) → `sst deploy --stage production`. **All three jobs (`verify`, `deploy-staging`, `deploy-production`) are implemented as of 2026-07-31** — `deploy-production` is `needs: [verify, deploy-staging]` so production is always a staging-proven, manually-approved promotion of the same commit.

### 10.3 IaC ownership
Two layers, split by resource lifetime (implemented + **applied live 2026-07-31** — see `docs/PROGRESS.md` → "Foundational IaC layer"):

> **Correction applied 2026-09-10 — where CloudWatch alarms live.** The per-stage Lambda alarms used to sit in the Terraform layer, targeting function names **hand-copied into `terraform.tfvars`** after a deploy. That is silently fragile: any change forcing Lambda replacement gives the function a new name suffix, after which the alarms watch a function that no longer exists and — because of `treat_missing_data = "notBreaching"` — sit **permanently green** while monitoring nothing. An alarm that cannot tell you it stopped working is worse than no alarm. They now live in `sst.config.ts`, wired **by reference**, which is also what the lifetime rule below actually implies: an alarm on a per-stage Lambda is per-stage and disposable. The `web_function_name`/`pdf_function_name` variables are gone.
>
> The split that remains is **by metric region**, and it is forced rather than chosen: CloudFront and Route 53 publish metrics **only to us-east-1**, and a CloudWatch alarm can only notify an SNS topic in its own region. The deploy role is scoped to eu-central-1 (with a narrow ACM-only us-east-1 carve-out), so `sst deploy` structurally *cannot* create those — hence `infra/terraform/uptime.tf` and a second, us-east-1 SNS topic (which needs its own subscription confirmation).
- **SST** (`sst.config.ts`, repo root): the app-native, per-stage, disposable resources — Lambda functions (Web + isolated Pdf), CloudFront, S3, the app's Route 53 **records** (via a zone *lookup*, not zone creation), the SES identity (Phase 4b), the **SSM parameter holding the Web CloudFront distribution ID** (`/bulbau-lu/<stage>/web-cdn-distribution-id`, created *after* the Nextjs component to break the SST #5990 cycle — the server function reads it at runtime for on-demand CDN invalidation, §6.2), and Payload's environment wiring. These are torn down/rebuilt with the stage.
- **Foundational Terraform** (`infra/terraform/`): the long-lived, stateful resources that must **outlive** any app deploy and so must not be owned by the removable SST stage — the Route 53 **hosted zone + reusable delegation set** (stable nameservers), the **Neon project/branch** (import-managed, `prevent_destroy`), the **GitHub-Actions deploy IAM role + policy** (making the committed `infra/aws/*.json` the single source of truth — file = live), and the **account cost/observability guardrails** (AWS Budgets, the `bulbau-lu-ops-alerts` SNS topic, and — opt-in via `manage_uptime_monitoring` — the us-east-1 uptime/CloudFront alarms in `uptime.tf`). Remote state in S3 with native locking. This is what the original "standalone Terraform lives in `infra/`" intent (and the earlier plan to model Neon via SST-consumed providers) resolved to in practice: a dedicated foundational stack, kept separate from SST so a stage teardown can never touch DNS or the database.

### 10.4 Why not CDK
CDK/CloudFormation is AWS-only and cannot declare the Neon database as code, which this project needs from day one. CloudFormation/CDK's automatic rollback-on-failure is a genuine advantage over Terraform's fail-forward model, but it doesn't offset the multi-provider gap, and it isn't foolproof either (a failed rollback can itself get stuck). SST's own engine made the same call — it moved off CDK onto Pulumi/Terraform providers for exactly this reason.

### 10.5 Database schema migrations (adopted 2026-07-07; live on staging 2026-07-08)

Payload's Drizzle Postgres adapter has two schema-management modes; this project uses each where it's correct:

- **`push` (dev + CI tests, `NODE_ENV !== 'production'`)**: schema is auto-synced to the config on boot. The local dev DB and the ephemeral CI Postgres are disposable sandboxes, so no migration run is needed there — this keeps local iteration fast and is Payload's own recommended dev workflow. Set explicitly in `src/payload.config.ts` (`push: pushSchema`, i.e. `NODE_ENV !== 'production'`) so the boundary is documented, not implicit — and, since 2026-09-16, **guarded**: push mode against a non-local `DATABASE_URL` refuses to start (see "Local-push guard" below).
- **Tracked migrations (deployed stages, `NODE_ENV === 'production'`)**: `push` is OFF; schema changes **only** via the SQL migrations in `src/migrations/` (committed, TypeScript, with `up`/`down`). Generated with `npm run migrate:create`, applied with `npm run migrate`.

**Where migrations run: CI, before deploy — not at runtime.** The `deploy-staging` job runs `payload migrate` before `sst deploy`, so the schema is applied once per deploy and is never older than the code that will read it. Payload's `prodMigrations` (run-at-init) option is deliberately **not** used: on Lambda it would run on every cold start and let concurrent cold starts race on DDL — that option is for long-running containers, which is a Phase B consideration, not Phase A. If a migration fails, the job stops and no code is deployed.

**Neon pooled vs. direct.** The app's runtime `DATABASE_URL` is Neon's **pooled** (`-pooler`) URL — correct for many short Lambda connections through PgBouncer. Migrations (DDL) must use the **direct/unpooled** URL instead, because PgBouncer's transaction pooling breaks schema changes; the CI migrate step uses the `STAGING_DATABASE_URL_UNPOOLED` GitHub Environment secret for this.

**History.** Staging was baselined with `migrate:fresh` on 2026-07-08 and production on 2026-07-31; both were then found to have been dev-pushed against (see the fail-closed step below) and were **reset from empty on 2026-09-16** — `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` on each branch's direct URL, then a push whose deploy jobs applied all four migrations in one batch (`migrate:verify` ✅ 4 rows each, CI run 35095817327). After launch a reset is never an option again: forward migrations only, Neon PITR for disasters.

**CI schema-drift guard.** The `verify` job runs `payload migrate:create --skip-empty` and fails via `git status --porcelain src/migrations` if a migration would have been written — the equivalent of Django's `makemigrations --check` (Payload has no `--check` flag; `</dev/null` + `timeout` neutralise the interactive rename prompt). Without it the push-mode `verify` job passes on a schema change that the migrations-only deploy then never applies.

**CI generated-artifact drift guard.** The `verify` job regenerates `src/payload-types.ts` + `src/app/(payload)/admin/importMap.js` and fails on any diff (both generators run without a DB and are idempotent). A stale import map breaks the admin at runtime with no build error.

**Fail-closed migrate step.** `payload migrate` is interactive: on a database carrying Payload's dev-push marker (`payload_migrations` row `dev`, batch `-1`) it prompts and, with stdin closed, **exits 0 having applied nothing** — which every staging deploy did from 2026-08-01 to 2026-09-14 because the local `.env` pointed at the staging branch. Both deploy jobs now run `npm run migrate:verify -- --pre` (refuses a marker) → `timeout 600s npm run migrate </dev/null` → `npm run migrate:verify` (every committed migration must be recorded). `scripts/verify-migrations.mjs` is plain `pg` with no Payload boot; a database with no ledger table passes pre-flight ("fresh database").

**Local-push guard.** `src/payload.config.ts` throws at load when push mode would be on (`NODE_ENV !== 'production'`) and `DATABASE_URL` is not a local host (`src/lib/dbGuard.ts`; `ALLOW_REMOTE_DB_PUSH=true` overrides). Stage-targeted commands pass the URL explicitly — `npx cross-env NODE_ENV=production DATABASE_URL="<direct url>" npm run migrate`, `npx cross-env DATABASE_URL="<direct url>" npm run migrate:verify -- --pre` — never by editing `.env`. A running dev server keeps the connection it started with.

## 11. Migration path: serverless → containers

### 11.1 Trigger criteria (any one is sufficient to start planning the move)
- Sustained (not bursty) request volume where Lambda's per-invocation cost consistently exceeds what a fixed-capacity container would cost.
- Cold starts (app or database) becoming frequent enough to visibly affect user experience.
- Neon's free/low tier consistently exceeded.
- A business requirement for formal uptime guarantees or compliance posture that Phase A doesn't offer.

### 11.2 Procedure
1. Provision RDS/Aurora Postgres; `pg_dump` the Neon database and `pg_restore` into it. No schema changes — same Payload Postgres adapter either way.
2. Build the existing codebase as a Docker image (validated continuously from early in Phase A, not created for the first time at cutover) and deploy to ECS Fargate behind an ALB, pointed at the restored database.
3. Smoke-test the container deployment against a copy of production data before cutover.
4. Swap CloudFront's origin from the Lambda function URL to the ALB. Domain, S3 media bucket, and DNS records are unchanged — no URL changes, no re-indexing, no visitor-facing disruption beyond the cutover window itself.
5. Decommission the Lambda app function and the Neon project once the container deployment is confirmed stable.

No content, media, translations, or configuration is ever tied to the compute choice — only S3 (media) and Postgres (everything else) hold state, and both are portable by design.

### 11.3 Scaling beyond the Phase B baseline

Worth being explicit about, since neither "Phase A" nor "Phase B" as scoped is an unlimited-scale claim: the Phase B baseline in Section 9 (single Fargate task, single-AZ database) is a starting point sized for this project's actual traffic, not a ceiling disguised as one. If real usage ever justified going further, the levers — in the order they'd actually get pulled — are: (1) Fargate target-tracking auto-scaling on CPU/memory or ALB request count, since the containers are already stateless and this requires no redesign; (2) Postgres read replicas, since this workload (a CMS-backed content site with a single admin) is overwhelmingly read-heavy; (3) a caching layer (e.g. ElastiCache) in front of the database only if read replicas stop being enough; (4) multi-region, only if the business ever had a genuine reason to need it. None of this is built now because none of it is justified by current traffic — but it's a deliberate next-steps list, not an unaddressed dead end.

## 13. Open risks & assumptions to validate early

- ~~Payload 3's "runs inside Next.js" model is proven on Vercel; running it via OpenNext on Lambda is architecturally equivalent but should be spiked in Phase 0 before other work depends on it.~~ **Resolved in Phase 0.** It works, but not out of the box — five real, non-obvious issues had to be fixed before it did, all now handled and documented in `docs/PROGRESS.md`: (1) OpenNext's build tracing copies externalized packages (`pg`, `pino`) into the Lambda bundle via symlinks, which Windows can't reliably produce as real Linux symlinks — builds must happen on Linux (CI), never locally on Windows. (2) `sharp` is excluded from the main server bundle by OpenNext by default and also ships architecture-specific binaries that don't cross-compile between an x64 CI runner and an arm64 Lambda — omitted entirely for now since nothing in the current Media collection uses it. (3) Payload's `admin/importMap.js` is generated, not static, and must be regenerated (`npm run generate:importmap`) whenever a collection, field, or plugin that contributes admin UI changes — silently stale otherwise, with no build-time error. (4) Media uploads need an explicit storage adapter (`@payloadcms/storage-s3`); SST linking a bucket only wires IAM permissions, it doesn't make Payload use it. (5) IAM's `aws:RequestedRegion` condition key doesn't meaningfully scope global services (CloudFront, IAM, Route 53) — a region-conditioned Allow silently doesn't cover them.
